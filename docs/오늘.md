  역할별 정책을 걸어도 View 로 보면 다 보인다 — 에러가 안 나서 모른다
- **`NULLIF(A, B)`** — 같으면 NULL. SQL 은 0으로 나누면 에러로 죽는다 (JS 는 NaN)

- **View 컬럼은 타입이 전부 `| null`** — Postgres 가 NOT NULL 을 보장 못 한다
- 🔴 **`.reverse()` 와 `.sort()` 는 원본을 바꾼다.** `[...배열]` 로 복사하고 뒤집는다
- **DB는 값을 주고 화면은 모양을 정한다** — `25.00` 이 JSON 에서 `25` 가 되므로
  화면에서 `toFixed(2)`

  최악은 2020-11-04 — 71개 중 7개, 수율 90.14%
- 5,232행일 때 안 보이던 것이 13행으로 접으니 보인다

파이썬은 **"쓸 때" 확인하지 "적을 때" 확인하지 않는다.**
컴파일러가 안 해주는 것을 테스트가 대신한다 (M26 의 이유)


- **S04 에서 수집기를 상시 구동할 때 같은 질문이 나온다**

**왜 HTTP 가 아니라 MQTT 인가**
```
HTTP   서버가 "새 데이터 있니?" 를 계속 묻는다 (폴링)
MQTT   설비가 "샷 나왔다" 를 생겼을 때만 말한다
```
- 1분에 1샷인데 1초마다 물으면 3,600번 중 60번만 데이터가 있다. 설비 100대면 100배
- 🔵 **데이터가 생기는 쪽이 말하게 하는 것** — 이게 전부다
- ⚫ S05 의 Supabase Realtime 도 프로토콜만 다르고 발상이 같다

**발행·구독 — 브로커가 둘을 가려준다**
- 발행자는 누가 받는지, 구독자는 누가 보냈는지 모른다. 브로커만 안다
- 수집기를 껐다 켜도 · 2개 붙여도 · 진짜 설비로 갈아끼워도 **반대편은 모른다**
- 🔵 월요일의 *"시뮬레이터는 DB 를 모른다"* 를 **구조가 강제하는 장치**가 브로커다.
  원칙을 말로 지키면 어겨지는데 구조가 지키면 어길 수가 없다

**★ 토픽 설계 — `shottrace/{equipment_id}/shot`**
```
후보                              버린 이유
shottrace/shot                    구독자가 설비별로 못 거른다
shottrace/plant1/line1/S14/shot   공장·라인이 하나뿐 — 항상 같은 값인 빈 계층
shottrace/S14/shot/{part_id}      토픽 가짓수가 무한 — 브로커 토픽 트리가 불어난다
shottrace/S14/shot                ✅ 채택
```
- 🔵 규칙: **구독자가 거르고 싶은 축만 토픽에, 나머지는 페이로드에**
- 🔴 가짓수가 무한한 값(시각·일련번호)을 토픽에 넣지 않는다
- 🔴 지금 하나뿐인 계층을 미리 파지 않는다. **계층은 나중에 앞에 붙일 수 있다**
- 형제를 같이 본다 — `status`(Last Will) · `alarm` 자리가 `shot` 축에서 나온다
- 구독 와일드카드: `+` 한 계층 / `#` 나머지 전부(**맨 끝에만**)

**페이로드 — JSON**
- 🔵 JSON 을 고른 이유는 **사람이 읽을 수 있어서.** 오늘 눈으로 검사한 것이 그 값어치.
  MessagePack·Protobuf 는 3~5배 작지만 못 읽는다. 느려지면 그때 바꾼다
- 🔴 `ISO = "%Y-%m-%dT%H:%M:%S+00:00"` — 타임존 없으면 받는 쪽이 자기 기준으로
  읽어서 **9시간 밀린다.** ADR 002 가 이미 UTC 로 정해놨다
- 🔴 `ensure_ascii=False` — 기본이 True 라 한글이 `가스` 로 나간다.
  **읽을 수 없는 로그는 없는 로그다**
- 🔴 빈 값은 키를 빼지 않고 `null` 을 적는다. "키가 없다"와 "값이 없다"는 다르다
- 🔵 `equipment_id` 가 토픽과 페이로드에 **둘 다** — 의도된 중복.
  저장하거나 로그에 남기면 **봉투는 사라지고 내용물만 남는다**

**🔴 자동 import 가 엉뚱한 걸 세 줄 넣었다**
```
from xmlrpc import client              ← "client" 이름만 보고 표준 라이브러리를 끌어왔다
from paho import mqtt                  ← 패키지다. Client 는 paho.mqtt.client 에 있다
from paho.mqtt import client as mqtt_client   ← mqtt 가 이미 쓰여서 이름이 바뀌었다
```
- `AttributeError: module 'paho.mqtt' has no attribute 'Client'`
- 🔴 `from xmlrpc import client` 가 제일 위험하다 — **에러가 안 난다.** 표준
  라이브러리에 진짜 있으니까. 지금은 지역변수가 덮어써서 안 터질 뿐이다
- 🔴 **자동 완성은 뜻을 모른다. 그 이름의 뭔가를 찾아줄 뿐이다. import 는 눈으로 본다**

**확인 — 보내봤다 ≠ 받았다**
```
터미널 B   docker exec shottrace-mosquitto mosquitto_sub -t "shottrace/#" -v
터미널 A   python services/simulator/replay.py --speed 3600 --limit 25
```
- 토픽 ✅ / `+00:00` ✅ / `"fail_reason": null` ✅ / parts 1개·2개 ✅ / 25건 ✅
- 🔴 `publish()` 는 토픽이 틀려도 JSON 이 깨져도 `loop_start()` 를 빼먹어도 에러가 없다

**관찰 두 가지**
- `59.52000045776367` — **CSV 원본이 그렇다.** float32 를 float64 로 옮긴 흔적.
  반올림하지 않는다. 파이프라인은 값을 나르고 **모양은 화면이 정한다** (ADR 008)
- 🔴 `parts` 배열 **순서가 매번 다르다.** `parts[0]` 을 LH 로 가정하면 조용히 틀린다.
  수집기는 `part_name` 으로 찾는다. **정렬해서 보내지 않는다** — 보장하면 기대게 된다

## 2026-09-26 토 · S03 — QoS · Last Will · 재연결 · 페이로드 완성

> 9/24 목 · 9/25 금을 건너뛰고 토요일에 목요일 분량을 했다.
> 일정표상 S03 은 9/28~10/4 인데 9/21 에 시작했으므로 **아직 3일 앞서 있다.**
> 자를 기능 없음. `docs/일정.md` 의 "한 달치까지 흡수" 범위 안.

**한 일**
- QoS 1 · Last Will · retain · `on_connect`/`on_disconnect` · `KEEPALIVE`
- 페이로드에 **공정변수 24개** (`values`) · `cycle_time` 을 그 안으로 옮김
- `--equipment` 기본값 `S14` — **한 프로세스 = 한 설비**

**QoS — "정확히 한 번" 은 프로토콜이 아니라 설계로 얻는다**
```
0  많아야 한 번   잃어도 모른다          왕복 1
1  적어도 한 번   중복될 수 있다         왕복 2   ← 채택
2  정확히 한 번   느리다                 왕복 4
```
- 샷은 잃으면 안 되지만 **QoS 2 를 안 쓴다.** 중복을 우리가 막을 수 있기 때문.
  `shot` PK `(equipment_id, measured_at)` 로 upsert 하면 두 번 와도 행이 안 는다
- 🔵 9/2 에 정한 PK 가 또 회수됐다. 인덱스 · RPC 조인 · 복합 FK 에 이어 네 번째
- 🔴 **QoS 는 구간별이다.** 발행 1 + 구독 0 = 그 구간은 0. S04 에서 다시 나온다
- 🔴 **QoS 가 보장 못 하는 것** — 구독자가 없을 때 보낸 메시지는 그냥 사라진다.
  수집기가 죽어 있는 동안의 샷은 잃는다. 지속 세션은 S04 의 문제

**Last Will — 죽은 뒤에 말하는 법**
```
Ctrl+C          finally 돈다   ✅
프로세스 강제종료 안 돈다        ❌   ← 공장에서 흔한 건 이쪽
전원/랜선        안 돈다        ❌
```
- 연결할 때 브로커에 유언을 맡긴다. 말없이 사라지면 브로커가 대신 발행
- 🔴 **정상 종료하면 유언이 안 나간다.** `disconnect()` 는 인사하고 가는 것이라
  브로커가 유언을 버린다 → 그 경로는 `finally` 에서 **우리가 직접** offline 발행
- 실측: `taskkill /F` → 1초 만에 offline 도착
- ⚫ **1초인 이유는 keepalive 가 아니다.** 프로세스가 죽으면 OS 가 TCP 를 닫아
  브로커가 즉시 안다. `keepalive` 는 **TCP 를 닫아줄 사람이 없는 경우**(랜선·정전)용.
  기본 60초는 공장에 느려서 `KEEPALIVE = 15`

**retain — 상태에는 켜고 사건에는 끈다**
```
상태 state   지금 살아있나 · 현재 온도    ✅ 최신 하나가 곧 진실
사건 event   샷 · 알람                    ❌ 하나하나가 다 의미
```
- 🔴 `shot` 에 켜면 새 구독자가 **옛날 샷을 방금 온 샷으로 오해**한다
- 실측: 구독을 새로 켜자마자 직전 실행의 `{"state":"offline"}` 이 즉시 왔다
- 🔵 S05 실시간 화면이 **켜지자마자** 가동 상태를 표시할 수 있는 근거
- ⚫ 수요일에 `shot` 과 `status` 를 다른 토픽으로 나눈 값어치가 여기서 나왔다.
  한 토픽에 섞였으면 retain 을 켤 수도 끌 수도 없다

**재연결 — 조용히 끊기는 것을 막는다**
- paho 는 알아서 재연결하지만 **말을 안 해준다.** 콜백으로 로그를 남긴다
- 🔵 `online` 발행을 `on_connect` 안에 두면 **최초 연결과 재연결이 같은 코드**를 탄다
- 🔴 재연결 뒤 `online` 을 다시 보내야 retain 된 `offline` 을 덮는다
- 🔴 `on_connect` 는 **실패해도 불린다.** `reason_code != 0` 을 안 보면
  연결 거부인데 "연결됨" 이라고 찍는다
- ⚫ 지수 백오프(1→2→4→…120초)는 thundering herd 방지. 기본값 그대로 쓴다

**🔴 연결은 비동기다 — 첫 시도에서 순서가 틀렸다**
```
틀림   shot → status online      구독자에겐 "죽은 설비가 샷을 보냈다"
맞음   status online → shot
```
- `connect()` 가 돌아와도 **CONNACK 전**이다. `on_connect` 는 그게 와야 불린다
- `client.is_connected()` 로 최대 5초 기다린 뒤 재생을 시작한다
- ⚫ S04 수집기에서 그대로 필요한 패턴

**🔴 한 연결 = 한 유언 = 한 설비**
- MQTT 는 연결당 유언이 하나뿐이라 설비 3대를 한 프로세스로 흉내낼 수 없다
- 실제 공장도 설비 하나 = 클라이언트 하나. **모델을 현실에 맞췄다**
- `--equipment` 기본값 `S14`. 3대를 돌리려면 터미널 3개
- 데이터가 결정을 쉽게 해줬다 — S14 2,624샷 / S01·S12 각 1샷

**페이로드 완성 — 공정변수 24개**
```
최상위 키   equipment_id · measured_at · values · parts
values      24개 (45 − 메타 9 − 죽은 12, ADR 003)
크기        1,111 B  →  1분에 1건이면 하루 1.6MB
```
- `cycle_time` 을 `values` 안으로. 공정변수 24개 중 하나일 뿐이다
- 🔴 `frozen=True` 인데 `dict` 를 넣었다. **껍데기만 언다** — 월요일에 `tuple` 을 쓴
  이유와 모순이지만 JSON 으로 그대로 나가야 해서 택했다.
  **"안 바꾼다"는 약속을 구조가 아니라 사람이 지킨다. 그게 비용이다**
- ⚫ NaN 을 미리 확인했다 — 24개 컬럼에 하나도 없다.
  🔴 있었으면 `json.dumps` 가 `NaN` 을 그대로 써서 **유효하지 않은 JSON** 이 됐다
- 🔴 컬럼명 소문자 변환은 **DB 를 본 게 아니다.** DB 컬럼명이 원본 CSV 를 따라
  지어졌을 뿐. 같은 원본에서 같은 규칙으로 나와 이름이 같아진 것이다

**⚫ 중복이 두 번째다**
`ISO` 에 이어 `META_COLS`/`DEAD_COLS` 가 `load.py` 와 겹쳤다.
**두 번은 참고 세 번째에 공용 모듈로 뺀다.**

**ADR 009 에 담은 것**
```
토픽    shottrace/{설비}/shot     QoS 1 · retain 끔
        shottrace/{설비}/status   QoS 1 · retain 켬
규칙    한 프로세스 = 한 설비 = 한 연결 = 한 유언
        measured_at 은 UTC + 오프셋 (ADR 002)
        values 24개 · 키는 원본 컬럼명 소문자 (ADR 003)
        parts 순서는 보장하지 않는다 — part_name 으로 찾는다
        빈 값은 키를 빼지 않고 null
```
- 버린 대안 7개. 제일 중요한 건 ⑦ **`product_id`·`lot_id` 를 안 넣은 것** —
  나머지는 성능·편의인데 이건 "시뮬레이터는 DB 를 모른다" 원칙이 달렸다
- 🔴 **남은 것 중 무서운 것 — 지속 세션.** QoS 1 을 써도 **구독자가 없으면
  메시지가 그냥 사라진다.** "잃지 않는다"고 믿는 게 위험하다. S04 에서 결정
- 인증·TLS 도 남았다 (`allow_anonymous true`)

**내가 멋대로 정한 두 가지 — 반론이 가능한 곳**
- 유언에 시각을 안 넣었다. 넣으면 "죽은 시각"이 아니라 "연결한 시각"이라 거짓말.
  `connected_at` 이라는 정직한 이름이면 쓸 수도 있지만 **쓸 데가 정해지지 않은
  필드는 계약만 무겁게 한다**
- `parts` 를 정렬해서 보내지 않는다. 보장하면 받는 쪽이 기대게 된다.
  **보기 편하려고 계약을 약하게 만들지 않는다.** 로그는 보는 쪽에서 정렬하면 된다

**🔑 S03 을 관통한 주제 5개**
1. **시계가 두 개다** — 재생 · MAX_GAP · monotonic · measured_at · 로그.
   버그 하나가 두 시계를 섞어서 나왔다
2. **순수한 것과 바깥세상을 나눈다** — to_shots/wait_for/topic_for/payload_for 가
   전부 왼쪽. M26 테스트 대상이 이번 주에 네 개 늘었다
3. **서로 모르게 만든다** — 브로커가 "시뮬레이터는 DB 를 모른다"를 **구조로 강제**한다.

**처음으로 스키마를 고쳤다**
```
지금까지  CREATE TABLE   비어 있는 데 만들었다
오늘      ALTER TABLE    5,232행이 든 테이블의 PK 를 바꿨다 — 한 행도 안 잃고
```
제약 6개 → 5개. UNIQUE 가 PK 에 흡수됐다.
```
shot_part_pkey   PRIMARY KEY (part_id)
              →  PRIMARY KEY (equipment_id, measured_at, product_id)
```

**ALTER TABLE 네 줄 — 순서가 전부다**
- 🔴 UNIQUE 를 **먼저** 지운다. 안 지우고 PK 를 추가하면 **같은 인덱스가 두 벌**이 된다.
  쓰기가 느려지고 디스크만 먹는데 **에러는 안 난다**
- 🔴 `PRIMARY KEY` 는 사실 **UNIQUE + NOT NULL 둘**이다. PK 를 떼도 NOT NULL 은 남으므로
  `ALTER COLUMN part_id DROP NOT NULL` 이 따로 필요하다
- 🔵 `BEGIN`~`COMMIT` — 1~3 사이에 "중복을 막는 게 없는" 구멍이 생기지만 트랜잭션 안이라
  아무도 못 본다. **Postgres 는 DDL 도 되돌릴 수 있다.** MySQL 은 안 된다 (S07 맛보기)
- 🔵 제약 기본 이름 규칙 — `{테이블}_pkey` · `{테이블}_{컬럼들}_key`.
  이 이름을 evidence ③ EXPLAIN 에서 이미 본 적 있다
- 🔵 인덱스 손해 없음 — 새 PK 가 옛 UNIQUE 와 **컬럼도 순서도 같아** 그대로 대체된다

**part_id 는 지우지 않고 nullable 로**
```
CSV 로 들어온 5,232행   part_id 있음
MQTT 로 들어올 행        part_id NULL
```
- 원본 추적(provenance)용. ADR 004 에서 중복 2,764행을 지운 근거가 `_id` 였다
- **값이 그 자체로 출처를 말해준다**

**번역 캐시 — part_name → product_id**
```
메시지마다 조회   왕복 6,565번
시작할 때 한 번   왕복 1번
```
- 🔴 캐시에는 **"언제 틀려지나"** 가 항상 따라온다. 제품 마스터는 1년에 몇 번 바뀐다
- 모르는 제품이 오면 **에러 로그 + 실패 카운트**. 자동 등록은 안 한다 —
  🔴 설비가 공백 두 칸짜리 이름을 보내면 **7번째 제품**이 생기고 파레토가 쪼개진다
- 🔵 `unknown` 검사를 **upsert 전에** 한다. 안 그러면 "샷은 있는데 부품이 없는" 상태가 생긴다

**🔴 두 테이블에 쓰는 문제 — 오늘은 기록만**
```
shot 은 됐는데 shot_part 에서 실패하면  →  공정변수는 있고 품질이 없는 샷
에러 안 남 · 화면에서 그냥 안 보임
```

- 🔴 진짜 해법은 트랜잭션인데 **PostgREST 로는 두 테이블을 한 트랜잭션에 못 묶는다.**

**upsert 는 준 컬럼만 덮어쓴다**

한 줄로 `DEFAULT now()` 를 쓰면 **기존 2,626행 전부에 "지금"이 채워진다.**
9월 초에 CSV 로 넣은 행이 "2026-09-30에 수집기로 받았다"고 말하게 된다 — 거짓말.
🔵 `NULL` 은 값 없음이 아니라 **"CSV 로 직접 들어온 행"** 이라는 정보다.
어제 `part_id` 를 nullable 로 남긴 것과 같은 발상 — **값의 유무가 출처를 말한다.**
⚫ 인덱스는 안 걸었다. "최근 받은 것" 쿼리가 아직 없다 (ADR 007 규칙)

**🔴 여기서 순수함수가 깨질 뻔했다**
```python
"received_at": datetime.now(timezone.utc).isoformat()   # ❌ 함수 안에서 시계를 읽는다
def to_shot_row(msg: dict, now: datetime)               # ✅ 밖에서 받는다
```
- `datetime.now()` 는 바깥세상(시계)을 읽어서 **같은 입력에 다른 출력**이 된다 → 테스트 불가
- 확인: 고정 시각을 넣으니 `같은 입력 → 같은 출력: True`
- 🔵 **일반 규칙 — 시계 · 난수 · UUID 는 함수 안에서 만들지 말고 밖에서 받는다.**
  셋 다 "부를 때마다 달라지는 것"이고 셋 다 테스트를 불가능하게 만든다
- ⚫ 오늘의 5초가 M26(11월) 의 한 시간을 아낀다

**확인 — 한 행에 두 시계**
```
이벤트 2020-10-16 04:57:47    처리 2026-09-30 00:40:06
이벤트 2020-10-16 04:58:48    처리 2026-09-30 00:40:07
이벤트 2020-10-16 04:59:48    처리 2026-09-30 00:40:07

오른쪽 1초 안에 다 들어왔다 (3600배속)
```
🔵 **드디어 DB 가 눈에 보이게 변했다.** 이틀 동안 "결과가 같아서 과정을 못 구분"
했는데, 처리 시각을 기록하기 시작하니 저절로 풀렸다. 언제 뭐가 들어왔는지가 남는다.

**공짜로 얻은 것**
`received_at - measured_at` = **파이프라인 지연**. 진짜 설비면 0.2초쯤이고
30초로 늘면 어딘가 막힌 것이다. 지금은 6년이라 의미 없지만 컬럼이 있으니
진짜 설비를 붙이는 날 바로 쓴다. 9월 복습의 *"살아있는지 확인하는 장치"* 의 재료.

## 2026-10-01 목 · S04 — ⚠️ 진행 중 LOT · EXCLUDE 제약

**한 일**
- `db/migrations/009_lot_open.sql` — `btree_gist` + `EXCLUDE` 로 구간 겹침 차단
- 진행 중 LOT = `ended_at = 'infinity'`
- `format.ts` 에 `진행중`, LOT 상세 화면이 "진행 중" 을 표시
- 실험으로 제약이 실제로 막는 것을 확인

**① LOT 은 누가 만드나 — 수집기는 안 만든다**
메시지에 `lot_id` 도 `plan_date` 도 없다. 🔴 어제 `part_id` 와 같은 모양인데 **결론은 반대**다.
```
part_id     스키마가 틀렸다   → PK 를 바꿨다
plan_date   메시지가 맞다     → 설비는 계획일을 모르는 게 정상이다
```
- 계획일은 **작업지시(work order)** 에서 온다. 생산관리가 만들고 설비는 받아보지도 않는다
- 🔵 **LOT 과 샷을 잇는 건 시간이다** — ADR 001 시간 구간 조인이 바로 이것.
  "설비가 LOT 을 몰라도 어느 LOT 인지 알 수 있다" 가 그 설계의 요점이었다
- LOT 생성은 S06(실적 입력) 의 일. 오늘은 SQL 로 손으로 흉내냈다
- 🔴 **LOT 없는 샷 = 미할당 생산.** 화면에 안 보이고 수율에도 안 잡힌다.
  작업자가 LOT 을 안 열고 기계를 돌리면 실제로 일어난다 → 금요일 미결 목록

**② 진행 중을 어떻게 적나 — NULL vs 'infinity'**
```
NULL        "값이 없다"   → 조인마다 OR ended_at IS NULL. 한 군데만 빼먹어도 조용히 사라진다
'infinity'  "끝이 없다"   → 비교가 그냥 된다. SQL 을 한 글자도 안 고쳤다
```
- 🔵 Postgres 의 `timestamptz` 는 진짜 무한대를 가진다. `CHECK (ended_at > started_at)` 도 통과
- 🔵 **의미가 다르다.** 진행 중 LOT 의 끝은 **모르는 게 아니라 아직 안 온 것**이다
- ⚫ 어제는 `received_at` 에 NULL 을 골랐다. 거기선 "CSV 로 들어와 수신 시각을 **모른다**" 가
  맞았다. **상황이 뜻을 정한다**

**🔴 ③ 열린 구간은 미래를 전부 삼킨다**
S14 / CN7 LH 는 LOT 이 6개 (합 1,985개).
```
S14-20201016-CN7LH 원래      187개
그것을 'infinity' 로 열면   1,985개   ← 10.6배 · 뒤 5개 LOT 것을 전부 자기 것이라 주장
```
그리고 뒤의 LOT 들도 여전히 자기 것이라 주장한다 → **한 부품이 두 LOT 에 속한다.**
🔵 ADR 006 이 반열린 구간 `[시작, 끝)` 을 고른 이유가 "겹치지 않게" 였는데,
**끝이 무한대면 그 보장이 통째로 날아간다.**
🔵 진짜 공장이면 열린 LOT 뒤에 닫힌 LOT 이 있을 수 없다. 시간은 앞으로만 간다.
🔴 **그래도 "안 터질 것" 에 기대면 안 된다** — 작업자가 마감을 깜빡하면 똑같이 일어난다

**④ EXCLUDE 제약 — 겹침은 두 행 사이의 관계다**
```
UNIQUE   같은 값이 두 번   한 컬럼(들)의 값
CHECK    한 행 안의 조건
EXCLUDE  "이 조합이 동시에 존재하면 안 된다"   ← 겹침은 여기
```
```sql
EXCLUDE USING gist (
    equip_cd                        WITH =,
    product_id                      WITH =,
    tstzrange(started_at, ended_at) WITH &&
);
```
- 🔵 UNIQUE 는 `WITH =` 만 쓰는 **특수한 EXCLUDE** 다
- 🔵 `tstzrange(a,b)` 는 `[a,b)` **반열린 구간 타입** — ADR 006 에서 손으로 쓴 것을
  Postgres 가 타입으로 가지고 있다. `&&` 가 "겹친다"
- 🔵 UNIQUE·PK·EXCLUDE 가 전부 인덱스로 구현된다. **인덱스는 "빨리 찾기" 이면서
  "중복 막기" 도구다** — 9월의 부분 인덱스와 같은 물건의 다른 얼굴
- ⚫ `btree_gist` 확장 필요 — gist 에 평범한 등호를 같이 쓰려면
- 🔴 **제약을 걸면 기존 데이터 전체가 검사된다.** 미리 세어보니 겹치는 쌍 0개라 통과했다

**실험 — 제약이 진짜로 막았다**
```
2️⃣ 위험한 LOT 열기 → ERROR 23P01: conflicting key value violates
   exclusion constraint "lot_no_overlap"
   DETAIL: (S14, 1, ["2020-10-16 04:58:48+00", infinity)) conflicts with
           (S14, 1, ["2020-10-19 23:24:46+00","2020-10-20 06:20:15+00"))
3️⃣ 안전한 LOT(마지막) 열기 → 성공 · get_lot_shots 는 463 그대로
```
🔵 **DB 가 "누구와 왜" 겹치는지까지 말해준다.** 좋은 에러 메시지는 "안 된다" 가 아니라
"무엇과 왜 안 되는지" 를 말한다. `23P01` 은 exclusion_violation 의 표준 코드 (S06 에서 쓴다)
🔵 **구조가 지킨다** — 9월 복습 5번 주제

**🔴 ⑤ 새 상태를 만들면 그 상태를 모르는 코드가 깨진다**
```
수집기   measured_at 비교만 한다            ✅
RPC      measured_at < infinity 가 참이다   ✅
화면     RangeError: Invalid time value     🔴 lib/format.ts:16 날짜()
```
```
PostgREST   "ended_at": "infinity"
JS          new Date("infinity") → Invalid Date · Intl 은 예외를 던진다
```
- 🔵 `'infinity'` 의 장점이 "쿼리를 안 고쳐도 된다" 였고 그건 맞았다.
  **공짜가 아니라 비용이 화면으로 옮겨간 것이다.** 설계 선택은 거의 항상 이 모양
- 🔵 **경계를 넘으면 타입이 바뀐다** — SQL 의 진짜 값이 JSON 에선 그냥 문자열
- 고치기: `format.ts` 에 `진행중(iso) => iso === "infinity"` 하나.
  **"infinity" 를 아는 곳이 한 군데** (ADR 002 의 규칙)
- 🔴 `분` 을 `NaN` 이 아니라 `null` 로. **NaN 은 "계산 실패", null 은 "계산 안 함"**.
  그냥 두면 화면에 `NaN분` 이 찍힌다
- 🔴 `!진행 && !같은날(...)` — **순서.** 단축 평가 덕에 `같은날` 이 호출조차 안 된다.
  뒤집으면 왼쪽에서 터진다
- 🔴 고친 뒤 **끝난 LOT 도 같이 확인**했다. 새 상태를 넣다가 멀쩡하던 걸 깨뜨리기 쉽다

**열어둔 LOT 은 닫았다**
데모용으로 남길까 했지만 2020년에 끝난 LOT 을 "진행 중" 으로 두는 건 거짓이다.
**조용히 틀린 값을 DB 에 남기지 않는다.** 재현 방법은 이 기록에 있고,
S06 에서 진짜 열린 LOT 이 생기면 그때 자연스럽게 본다.

**🔴 아직도 못 한 것 — DROP NOT NULL 검증 (나흘째)**
여전히 전부 UPDATE 다. 새 샷이 INSERT 되는 경로를 아직 안 탔다.

- `apps/web/lib/supabase/client.ts` — 브라우저용 클라이언트
- `apps/web/app/LiveRefresh.tsx` — 구독 → 1초 throttle → `router.refresh()`
- `page.tsx` — `revalidate` 60 → 0
- 🔁 collector Dockerfile 은 화요일 아침으로 미뤘다. ①이 일을 하나 늘려서

**① 실시간을 붙이려다 "숫자가 안 변한다" 를 먼저 만났다**
```
수집기가 쓰는 곳   shot · shot_part
현황판이 읽는 곳   plant_summary → FROM production_lot (저장 집계)
```
겹치는 게 없다. **알림이 완벽하게 와도 다시 조회한 숫자가 같다.**
🔵 `decisions/README.md` 의 미결이 **전제조건으로 승격**했다. 실시간은 "미결을 나중에"
가 안 되는 기능이다 — 숫자가 안 움직이면 기능 자체가 성립하지 않는다.

버린 대안
- **B 수집기가 `production_lot` 집계도 갱신** — 트랜잭션·동시성 이야기가 열린다.
  그건 S07 칸에 이미 있다. 오늘 당기면 S05 가 S07 을 먹는다
- **C 범위 축소(`shot` 기반 조각만 실시간)** — 현황판 큰 숫자는 그대로 죽은 채로 남는다.
  목요일 MVP 점검에서 바로 들통난다
- **A 선택** — 샷이 원본이고 집계는 파생. ADR 008 에서 이미 정한 방향이다

**🔴 먼저 세어보고 바꿨다** (9월 EXCLUDE 때와 같은 습관)
```
production_lot 합   5,232
shot_part COUNT     5,232 · 양품 5,172 · 불량 60
```
🔵 **두 집계가 정확히 일치했다. "안 달라졌다" 가 제일 좋은 결과다** — 같은 숫자를
다른 길로 구해서 같은 답이 나왔으니 교체가 안전했다는 증거다. 그리고 **미할당 생산 0건**
이라 미결 하나가 "해당 없음" 으로 닫혔다.

**② 🔴 입도가 다른 둘을 한 번에 조인하면 곱해진다 (fan-out)**
설비별 집계는 수량(`shot_part`)과 LOT 개수(`production_lot`)를 같이 봐야 한다.
둘을 그냥 `LEFT JOIN` 두 번 하면
```
LOT 2건 × 부품 3행 = 6행      COUNT(부품) 3 → 6 · COUNT(LOT) 2 → 6
```
🔴 **에러가 안 난다.** 분자·분모가 같이 부풀어 수율은 멀쩡해 보이고 생산량만 틀린다.
해법은 **각자 1행으로 접은 뒤 붙이기** — CTE 두 개(`part_agg` · `lot_agg`).
✍️ **서로 다른 입도를 한 번에 조인하지 않는다.**

**③ 🔵 알림 ≠ 데이터 — 오늘의 핵심 문장**
```
payload 로 숫자를 고친다   → 수율을 브라우저가 계산하게 된다 (ADR 008 을 뒤집는다)
payload 를 신호로만 쓴다   → 값은 다시 DB 에 묻는다
```
✍️ **이벤트는 타이밍만 알려준다. 값은 언제나 DB 에서 온다.**

이 선택이 함정 둘을 **미리** 지웠다.
- `REPLICA IDENTITY FULL` 이 필요 없다 — 바뀌기 전 값을 안 쓰니까
- 재연결 복구 코드가 필요 없다 — "다시 조회" 가 유일한 갱신 경로라서

**④ 🔴 Realtime 이 못 보는 것 둘**
Realtime 은 테이블을 들여다보는 게 아니라 **WAL(변경 일지)** 을 읽는다. 그래서
```
View          저장된 행이 없다       → 구독해도 알림이 없다
명단 밖 테이블  일지에서 걸러진다       → 구독해도 알림이 없다
```
🔴 **둘 다 `SUBSCRIBED` 가 뜨고 에러도 없다.** 조용히 아무 일도 안 일어난다.

**⑤ 🔴 그 "조용히" 를 실제로 한 번 겪었다**
마이그레이션을 아직 실행하지 않은 상태에서 `SELECT * FROM plant_summary` 가 멀쩡히
나왔다. 바뀐 View 와 옛 View 의 **숫자가 같아서(①) 화면으로는 구분이 안 됐다.**
```
SELECT viewname, definition FROM pg_views ...
  → count(l.lot_id) · sum(total_qty)   옛 코드였다
```
🔵 **"DB 에 뭐가 들어갔나" 는 파일이 아니라 카탈로그에 묻는다.** 파일에 쓴 것과
DB 가 받아들인 것은 다른 것이고, 진실은 후자다.

**⑥ 캐시를 켜둔 채로는 실시간이 아니다**
`revalidate = 60` 이면 `router.refresh()` 를 불러도 **묵은 화면이 올 수 있다.**
알림도 오고 새로고침도 되는데 숫자만 안 바뀐다 — 오늘 세 번째 "조용한" 자리였다.

**⑦ 쏟아짐 — throttle 1초**
60배속 · 설비 3대면 `shot_part` INSERT 가 초당 6건, 현황판은 View 2개를 읽으니
**초당 12 왕복**이다. 탭 3개면 36.
```
알림이 오면        메모지(useRef)에 "바뀜" 만 적는다
1초마다 타이머가    적혀 있으면 지우고 router.refresh()
```
🔵 debounce 는 검색창용이다 — "조용해질 때" 를 기다리므로 **생산이 계속되면 영원히
안 돈다.** 실시간 화면은 throttle 이 맞다. 사람 눈에는 1초면 충분히 살아 있다.

**실험 — 숫자가 진짜 움직인다** ✅
```
INSERT 1건   생산 5,232 → 5,233 · S14 5,230 → 5,231   (1초 이내 · 새로고침 없음)
DELETE       5,233 → 5,232                            (지우는 것도 실시간)
```
🔵 그때 **`LOT 25건` 은 그대로였다.** 방금 넣은 샷은 어느 LOT 에도 안 속한 샷이라서다.
"LOT 수와 생산량은 기준이 다른 두 숫자" 라는 게 눈앞에 나타났다.
✅ **`DROP NOT NULL` 검증** — `part_id` 없이 INSERT 하는 경로를 **처음** 탔다. 나흘 밀렸던 것.

**🔴 새로 안 것 — 재생으로는 숫자가 안 움직인다**
`replay.py` 는 원본 `measured_at` 을 그대로 보낸다. 수집기의 `upsert` 는 이미 있는 행을
만나 **UPDATE** 가 된다. 새 행이 안 생기니 수량이 그대로다.
🔵 **고장이 아니라 멱등성이다.** 9월에 일부러 그렇게 만들었고 그 판단은 지금도 맞다.
🔴 다만 **"살아 움직이는 화면" 을 보여주는 용도로는 안 맞는다.** 목요일 MVP 점검 전에
데모용 새 데이터를 어떻게 만들지 정해야 한다.

- LOT 상세도 실시간 — `shot` 을 발행 명단에 추가

## 2026-10-07 수 · S05 — 화면이 혼자 움직인다 · ● 수신 중

**한 일**

- `scripts/demo/demo_lot.sql` — 데모 LOT 열기 · 닫기 · 치우기

- `LiveRefresh` — `● 수신 중` / `○ 연결 끊김`
- **진짜로 흘려봤다.** 1배속 · 30샷 · 화면이 1분마다 혼자 올라간다

**① 🔴 시각을 옮길 때도 재생기와 같은 규칙을 써야 한다**
순진하게 `원본 + (지금 − 첫 샷)` 으로 더하면 **구멍에서 깨진다.**
```
원본 간격 3시간   measured_at 은 3시간 뛴다
재생기           300초만 기다린다 (MAX_GAP)
                 🔴 어긋난 만큼 measured_at 이 미래로 간다
```
그래서 `to_live` 는 `wait_for` 를 **그대로 불러서** `due` 를 누적하고 그걸 시각에 쓴다.
```
원본 00:00:00 → 09:00:00
원본 00:01:00 → 09:01:00      +60초 그대로
원본 05:00:00 → 09:06:00      🔵 5시간 구멍이 5분으로 접혔다
```
✍️ **같은 규칙이 두 군데 필요하면 함수를 재사용한다. 복사하면 언젠가 어긋난다.**
🔵 `frozen` 이라 고치는 게 아니라 `replace` 로 사본을 만든다. 원본 리스트가 안 상한다.

**② `--speed` 의 기본값을 없앴다**
```
default=3600.0 이면   "사용자가 3600을 골랐다" 와 "그냥 기본값이다" 를 구분 못 한다
```
기본값을 `None` 으로 두고 나중에 직접 채운다. 그래야 `--live --speed 60` 이라는
**모순을 잡아서 `p.error` 로 거부**할 수 있다. 조용히 한쪽을 이기게 하지 않는다.
🔴 `--live` 는 1배속이어야 한다. 빠르게 하면 `measured_at` 이 미래로 달아난다 (ADR 010 ②).

**③ 진행 중 LOT 이 화면에 처음 나왔다**
10/1 에 만들고 엿새 만이다. `ended_at = 'infinity'` → 화면에 초록색 **"진행 중"**.
🔵 **만들어두고 보여줄 데가 없던 기능**이었다. 데모 LOT 이 그 자리를 만들어줬다.
EXCLUDE 제약도 같이 일했다 — INSERT 가 통과했다는 건 열린 LOT 이 또 없다는 뜻이다.

**④ 🔴 한 화면에서 두 숫자가 서로 달랐다**
```
샷 이력    3개     RPC 가 세어온 진짜 개수
수율 카드  0 / 0   production_lot 의 저장값 → NaN%
```
어제 현황판에서 고친 *"저장 집계가 낡는다"* 가 **LOT 상세에는 그대로 남아 있었다.**
🔵 어제는 안 보였다. 2020년 LOT 은 이미 끝나서 저장값이 정확했으니까.
**진행 중 LOT 을 만드니까 드러났다.**
- `tally(shots)` 순수함수로 빼서 샷에서 직접 센다 (`pareto` 옆자리 · M26 테스트 대상)
- 🔴 `total ? ... : null` — **0 은 "전부 불량", null 은 "아직 모른다"**.
  월요일에 `COALESCE` 를 수율에만 안 쓴 것과 같은 판단이다
- 빈 상태 — `—` 와 "아직 들어온 샷이 없다"

**⑤ `useRef` 와 `useState` 가 여기서 갈린다**
```
useRef     바뀌어도 화면을 안 그린다   → "바뀜" 메모지 (월요일)
useState   바뀌면 화면을 다시 그린다   → 연결 상태 (오늘)
```
✍️ **화면에 보여야 하면 `useState`, 안 보여도 되면 `useRef`.**
🔴 색만으로 구분하지 않는다 (M09) — `● 수신 중` / `○ 연결 끊김`, 글자가 뜻을 진다.

**⑥ 🔴 JSX 안에서는 주석 모양이 다르다 — 이틀 연속 같은 계열**
```
JS 자리     // 주석
JSX 안쪽    {/* 주석 */}      🔴 // 를 쓰면 화면에 글자로 찍힌다 (에러 아님)
```
어제는 Dockerfile 의 `#` 였다. **주석 규칙은 파일 형식마다 다르다.**

**⑦ 데모 데이터의 기준은 "2026년 이후"**
원본은 2020-10 ~ 11 뿐이라 섞일 수가 없다. 치우는 순서는 `shot_part` → `shot` (FK).
🔴 끝난 뒤에는 LOT 을 **닫는다.** 진행 중으로 두면 조용히 틀린 값이 남는다 (10/1 교훈).
닫을 때 저장 수량도 채운다 — 안 채우면 LOT 목록 화면이 `0개` 로 보인다.

**확인한 숫자**
```
생산 5,232 → 5,275        1분마다 1~2개씩 (샷 1번 = 부품 2개)
LOT  25 → 26건            데모 LOT 하나
데모 LOT   샷 21개 · 수율 100.00% · 양품 21/21 · 진행 중
```
🔵 **LOT 상세 21개 vs 현황판 +43** — 틀린 게 아니라 **둘이 다른 걸 센다.**
패밀리 금형이라 샷 하나에 부품이 둘이고, LOT 은 제품 하나만 받는다 (ADR 005).

**🔴 새로 안 미결 — LOT 목록은 아직 저장값을 본다**
`/lots` 는 `production_lot.total_qty` 를 그대로 보여준다. 진행 중 LOT 이 `0개` 로 나온다.
LOT 25건 전부에 시간 구간 조인을 돌려야 해서 **성능과 정확성의 교환**이다. 미결로 둔다.

**내일 할 것 (목 · MVP 점검)**

- 데모 LOT 닫기 (`demo_lot.sql` ②) · 필요하면 치우기
- 🔴 LOT 목록 저장값 미결을 어떻게 할지 판단

**MVP 를 무엇이라고 보았나**

세 조건 — ① 파이프라인 전체가 돈다 ② 실시간이다 ③ 로컬이 아니라 배포본이다. **셋 다 맞았다.**

**① 🔵 점검표를 먼저 적은 것이 오늘의 핵심이었다**
해보고 나서 적으면 **"본 것" 만** 적게 된다. 먼저 적으면 **"아직 안 본 것"** 이 보인다.
7·8번(품질 · LOT 목록)은 **안 될 것 같아서 일부러 넣었다.** 성공할 것만 적으면 점검이
아니라 자랑이다.
```
화면만 봤다면       ✅ 만 남는다
표를 먼저 적었다면  7·8 이 들어간다
로그까지 봤다면     하이드레이션 경고 — 화면에는 안 보이던 것
HTML 을 읽었다면    같은 실수 두 군데 더
```
🔵 **발견 넷 중 셋은 "화면 보기" 로는 안 나왔다.**

**② 🔴 품질 화면 안에서 숫자가 어긋난다**
```
헤더     불량 60건 / 전체 5,232개     production_lot 저장값
파레토   36 + 15 + 10 = 61건          shot_part 원본
```
어제 LOT 상세에서 고친 것과 같은 모양이다. **저장 집계를 보는 화면이 아직 둘 남아 있었다.**

**③ 🔴 거짓말 둘을 지웠다 — `NaN%` 와 `0.00%`**
```
0.00%   "전부 불량이었다"       사실이 아니다
—       "아직 계산할 수 없다"   사실이다
```
10/1 에 "조용히 틀린 값을 DB 에 남기지 않는다" 고 했다. **화면도 같다.**
월요일에 정한 판단(`null` → `—`)을 두 자리에 더 적용한 것뿐이라 비용이 거의 없었다.

**④ 🔴 주석이 틀린 믿음을 적어두고 있었다**
```tsx
const rate = (lot.pass_qty / lot.total_qty) * 100;   // total 0 은 CHECK가 막음
```
실제 제약은 `total_qty >= 0` 과 `pass + fail = total` 뿐이라 **0 을 허용한다.**
🔵 **"제약이 막아줄 것" 이라고 믿고 쓴 코드는 제약을 직접 읽어서 확인해야 한다.**
진행 중 LOT(수량 0)을 만들고서야 드러났다 — 2020년 데이터만 있었으면 영원히 몰랐다.

**⑤ 🔴 하이드레이션 경고 — 화면에는 안 보이던 것**
```
In HTML, whitespace text nodes cannot be a child of <tr>.

<tr key={lot.lot_id} className="...">  {/* key = PK */}
                                      ↑↑ 이 공백이 "글자" 로 들어간다
```
🔵 하이드레이션 = 서버가 만든 HTML 에 브라우저가 React 를 덧씌우는 것. 둘이 다르면 경고가 난다.
🔴 **화면은 멀쩡하고 콘솔에만 찍힌다.** 점검표에 "로그를 본다" 가 없었으면 못 찾았다.
같은 실수가 `<LiveRefresh />` 뒤에도 둘 있었는데, **`<section>` 안이라 경고가 안 났다.**
자리에 따라 터지기도 하고 안 터지기도 한다.

**⑥ 이번 주에 주석으로 세 번 걸렸다**
```
화   Dockerfile   # 는 줄 맨 앞에서만
수   JSX          {/* */} 로 감싸야 한다
목   JSX          return ( 바로 뒤에는 못 쓴다 — 자식이 둘이 된다
목   JSX          태그 뒤에 두면 공백이 글자가 된다
```
✍️ **주석도 코드다.** 자리에 따라 문법이 달라진다.

**⑦ 12 멱등 — 조심해서가 아니라 구조로**
`--live` 없이 원본 5샷을 다시 보냈다.
```
전 5,314  →  재전송 5건  →  후 5,314      변화 없음
```
🔵 중복을 검사하는 코드는 한 줄도 없다. **PK 가 막는다.**
🔴 MQTT 는 QoS 1 이라 **중복 수신이 정상 동작**이다. 그때 두 배가 되지 않는 근거가 이 PK 다.

안 쓰는 넷을 빼고 **"아직 안 쓰는 것 — Zod(S06) · Vitest(S08)"** 로 자리를 옮겼다.
🔴 면접에서 제일 위험한 자리다. 스택에 적혀 있으면 **물어본다.** "아직 안 썼어요" 가
나오면 나머지 적어둔 것도 의심받는다. 옮겨 적으면 오히려 **계획이 있다는 증거**가 된다.

  띄운다" 는 **README 에 없으면 아무도 모른다**

**③ ADR 012 — 따로 보이는 결정이 한 덩어리일 때**
이번 주 결정이 여섯인데 ADR 을 여섯 개 쓰지 않았다. 기준은 **"하나가 바뀌면 나머지도
바뀌나"** 다.
```
"알림을 신호로만 쓴다" 를 뒤집으면
  → 집계가 브라우저로 넘어온다 · throttle 이 의미를 잃는다 · 놓친 알림을 세야 한다
```
서로를 떠받치고 있으므로 한 ADR 이다. ADR 010(가상 시계 + 진행 중 LOT)과 같은 판단.
- 버린 대안 7개를 적었다. 🔵 그중 둘은 **계획했다가 접은 것**(수집기가 집계 갱신 ·
  `shot` 을 명단에) 이라 설명이 강하다. "처음부터 안 한 것" 보다 낫다

**④ 🔴 ADR 012 의 남은 것 — S06 에서 반드시 같이 본다**
구독은 `anon` 키로 나가고 **알림에도 RLS 가 적용된다.** `USING (true)` 를 역할 기반으로
좁히는 순간 **알림이 조용히 끊길 수 있다.** S06 은 이미 "틀리면 조용히 뚫린다" 인 주인데
**"조용히 끊긴다" 가 하나 더 붙었다.**

**⑤ 데모 LOT 을 닫았다 — `Success` 는 "바뀌었다" 가 아니다**
`UPDATE` 는 `RETURNING` 이 없으면 **몇 줄을 고쳤든 "0 rows"** 로 나온다. 조건에 맞는 행이
없어도 똑같이 성공이다. 🔵 **확인은 데이터에 직접 묻는다.**
```
S14-20261007-CN7LH   10-07 09:29 ~ 10-09 08:02   39개 · 불량 1 · 97.44%
```
🔵 **이틀에 걸쳐 파이프라인이 실제로 쌓은 기록**이다. 가짜 데이터가 아니다.
🔵 ADR 006 은 `ended_at` 을 "마지막 샷 + 1초" 로 정했는데 여기서는 `now()` 를 썼다.
**불러오는 것과 지금 끝내는 것은 상황이 다르다.** S06 에서 실적 입력으로 LOT 을 닫게
되면 어느 쪽인지 정해야 한다 — ADR 006 에 꼬리로 붙는다.

**⑥ 🔵 화면마다 신선도가 다르다**
```
현황판 · LOT 상세   revalidate = 0    즉시
LOT 목록 · 품질     revalidate = 60   최대 1분 + 한 박자
```
Vercel 은 60초가 지나도 **첫 요청에는 묵은 걸 주고 뒤에서 새로 만든다**(stale-while-revalidate).
그래서 새로고침을 두 번 해야 바뀐다. 🔴 의도한 것이지만 **사용자는 어디가 실시간인지
모른다** → 미결에 추가.

**📕 S05 를 관통한 주제 5개**
1. **알림은 신호, 값은 DB 에서** — 이 한 줄이 S05 전부다
2. **집계는 저장값이 아니라 원본에서** — 실시간은 미결을 미룰 수 없다
3. **경계를 넘으면 가정이 깨진다** — `parents[2]` · `localhost` · "CHECK 가 막음"
4. **조용히 틀리는 것이 다섯 번** — 명단 누락 · View 구독 · 캐시 · 하이드레이션 · `0.00%`
5. **점검은 적어놓고 지우는 것** — 발견 넷 중 셋이 화면 아닌 콘솔·로그·HTML 에서 나왔다

**30초 설명 (2월 R07 설명 훈련용 초안)**
> 수집기가 DB 에 쓰면 Postgres 의 변경 일지를 Supabase Realtime 이 읽어 브라우저로
> 밀어준다. 그 알림은 **값으로 쓰지 않고 신호로만** 쓴다 — 받으면 서버에 다시 묻는다.
> 집계를 브라우저가 하면 DB 에 집계를 둔 의미가 없어지기 때문이다. 초당 여섯 건까지
> 오는데 1초에 한 번만 다시 묻도록 묶었고, 덕분에 연결이 끊겼다 붙어도 놓친 알림을
> 셀 필요가 없다. 다시 묻는 것이 유일한 갱신 경로라서다.

**② 📘 USING 과 WITH CHECK**

|---|---|---|

| 늦게 온 신호 | 그 사이 작업이 바뀌면 엉뚱한 곳에 붙는다 | 측정 시각으로 맞게 잇는다 (ADR 010) |

**① 📘 OEE = 가동률 × 성능 × 품질** (택시 기사의 하루)
```
가동률 = 가동 ÷ (가동 + 셋업 + 계획 외 정지)   계획 정지는 분모에서 뺀다 · 셋업은 손실 (020)
성능   = (샷 수 × 표준 사이클타임) ÷ 가동       100% 상한
품질   = 양품 ÷ 전체
```
**② 🔴 100% 상한이 버그를 숨긴다** — 패밀리 금형은 한 샷에 부품 둘. 성능에 부품 수를 넣으면 200%가 잘려 100% 로
보이고, 진짜로 느려져도(133%) 여전히 100%. → **샷 수**로 계산하고, 자르기 전 값(`performanceRaw`)도 같이 돌려준다.

**③ 📘 순수함수** — 같은 입력 → 같은 출력, 바깥을 안 본다. `import` 가 하나도 없다. S04 수집기의
`to_shot_row(msg, now)`(시계를 밖에서 받기)와 같은 생각. 분모 0 → **null** (0% 는 거짓말 — 9월 수율과 같은 규칙).

**확인 — DB · 화면 없이 숫자만 넣어서**
| 경우 | 결과 |
|---|---|
| 택시 하루 | 80% · 90% · 95% → OEE 68% |
| 느려짐 · 샷 수로 | 성능 67% → 보인다 |
| 느려짐 · 부품 수로 (실수) | 성능 100% (자르기 전 133%) → OEE 100% 🔴 상한이 숨겼다 |
| 안 돌린 날 | 전부 null |
