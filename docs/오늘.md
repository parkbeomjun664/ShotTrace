**배운 것**
- **PK·UNIQUE 는 인덱스를 자동으로 만들고 FK 는 안 만든다.** 기존 7개가 전부
  PK·UNIQUE 에서 나온 것이었다
- **왼쪽 접두사 규칙** — 복합 인덱스 `(A,B,C)` 는 왼쪽부터 연속으로만 쓴다
- 🔴 **등호 먼저, 범위 나중.** 범위 조건 **다음 컬럼부터는 인덱스로 못 좁힌다**
  → 기존 `UNIQUE(equipment_id, measured_at, product_id)` 는 범위가 중간에 껴서
    `product_id` 를 못 쓴다. 375행을 읽고 절반을 버린다
  → `(equipment_id, product_id, measured_at)` 로 걸어야 187행만 읽는다
- **부분 인덱스** — 불량이 60/5,232(1.15%)라 색인이 87배 작아진다.
  선택도가 낮을수록 효과가 크다
- **FK 라고 반사적으로 걸지 않는다** — 쓰는 쿼리가 있을 때 건다

- EXPLAIN 4종 실측 → `docs/evidence/003-indexes-explain.md` (목요일 것을 당김)

- 일정 재수립 — 12/31 → **11/26 완성**. 하루 분량 기준을 "산출물 하나"로

**한 일**

- ADR 008 · 타입 재생성

**배운 것**
- **View 는 데이터를 안 갖는다.** "이렇게 조회하라"는 설명서만 갖는다
- 🔴 **`security_invoker = on` 을 빼면 View 가 RLS 를 우회한다.** S06 에서
  역할별 정책을 걸어도 View 로 보면 다 보인다 — 에러가 안 나서 모른다
- **`NULLIF(A, B)`** — 같으면 NULL. SQL 은 0으로 나누면 에러로 죽는다 (JS 는 NaN)
- **`100.0`** — 정수끼리 나누면 소수점이 버려진다
- **윈도우 함수 `OVER ()`** — `GROUP BY` 로 접은 **뒤** 결과 전체를 훑는다.
  `GROUP BY` 만으로는 "전체 대비 비율"을 못 만든다
- **View 컬럼은 타입이 전부 `| null`** — Postgres 가 NOT NULL 을 보장 못 한다
- 🔴 **`.reverse()` 와 `.sort()` 는 원본을 바꾼다.** `[...배열]` 로 복사하고 뒤집는다
- **DB는 값을 주고 화면은 모양을 정한다** — `25.00` 이 JSON 에서 `25` 가 되므로
  화면에서 `toFixed(2)`

**새로 보인 사실**
- 불량 60건이 **6일에 몰려 있다.** 13일 중 7일은 무결점.
  최악은 2020-11-04 — 71개 중 7개, 수율 90.14%
- 5,232행일 때 안 보이던 것이 13행으로 접으니 보인다

**내일 할 것**

**배운 것**

- **`RETURNS TABLE`** — 개수·순서·타입이 안쪽 SELECT 와 정확히 같아야 한다
- **변동성** `IMMUTABLE` / **`STABLE`**(읽기만) / `VOLATILE`(기본값)
  → 안 적으면 옵티마이저가 매번 다시 부른다
- 🔴 **`SET search_path = ''`** — 함수가 **가짜 테이블을 읽게 되는 공격**을 막는다.
  대신 `public.` 을 전부 붙여야 한다
- **`$$`** 달러 인용 — 파이썬의 `"""` 같은 것
- 🔴 **생성된 타입도 틀린다.** View 는 전부 `| null`(과하게 안전),
  RPC 는 전부 non-null(**거짓말** — `fail_reason` 은 NULL 이 온다)
  → `Omit<T,"k"> & { k: 새타입 }` 으로 손으로 좁히고 **이유를 주석에 남긴다**
- **RPC 결과는 평평하다** — 임베드의 `s.shot?.cycle_time` 이 `s.cycle_time` 이 된다
