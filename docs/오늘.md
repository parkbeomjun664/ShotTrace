- 🔴 **`security_invoker = on` 을 빼면 View 가 RLS 를 우회한다.** S06 에서
  역할별 정책을 걸어도 View 로 보면 다 보인다 — 에러가 안 나서 모른다
- **`NULLIF(A, B)`** — 같으면 NULL. SQL 은 0으로 나누면 에러로 죽는다 (JS 는 NaN)

- **윈도우 함수 `OVER ()`** — `GROUP BY` 로 접은 **뒤** 결과 전체를 훑는다.
  `GROUP BY` 만으로는 "전체 대비 비율"을 못 만든다
- **View 컬럼은 타입이 전부 `| null`** — Postgres 가 NOT NULL 을 보장 못 한다
- 🔴 **`.reverse()` 와 `.sort()` 는 원본을 바꾼다.** `[...배열]` 로 복사하고 뒤집는다
- **DB는 값을 주고 화면은 모양을 정한다** — `25.00` 이 JSON 에서 `25` 가 되므로
  화면에서 `toFixed(2)`

**새로 보인 사실**

  최악은 2020-11-04 — 71개 중 7개, 수율 90.14%
- 5,232행일 때 안 보이던 것이 13행으로 접으니 보인다

파이썬은 **"쓸 때" 확인하지 "적을 때" 확인하지 않는다.**
컴파일러가 안 해주는 것을 테스트가 대신한다 (M26 의 이유)

- **S04 에서 수집기를 상시 구동할 때 같은 질문이 나온다**

**왜 HTTP 가 아니라 MQTT 인가**
```
HTTP   서버가 "새 데이터 있니?" 를 계속 묻는다 (폴링)
MQTT   설비가 "샷 나왔다" 를 생겼을 때만 말한다
```
- 1분에 1샷인데 1초마다 물으면 3,600번 중 60번만 데이터가 있다. 설비 100대면 100배
- 🔵 **데이터가 생기는 쪽이 말하게 하는 것** — 이게 전부다
- ⚫ S05 의 Supabase Realtime 도 프로토콜만 다르고 발상이 같다

**발행·구독 — 브로커가 둘을 가려준다**
- 발행자는 누가 받는지, 구독자는 누가 보냈는지 모른다. 브로커만 안다
- 수집기를 껐다 켜도 · 2개 붙여도 · 진짜 설비로 갈아끼워도 **반대편은 모른다**
- 🔵 월요일의 *"시뮬레이터는 DB 를 모른다"* 를 **구조가 강제하는 장치**가 브로커다.
  원칙을 말로 지키면 어겨지는데 구조가 지키면 어길 수가 없다

**★ 토픽 설계 — `shottrace/{equipment_id}/shot`**
```
후보                              버린 이유
shottrace/shot                    구독자가 설비별로 못 거른다
shottrace/plant1/line1/S14/shot   공장·라인이 하나뿐 — 항상 같은 값인 빈 계층
shottrace/S14/shot/{part_id}      토픽 가짓수가 무한 — 브로커 토픽 트리가 불어난다
shottrace/S14/shot                ✅ 채택
```
- 🔵 규칙: **구독자가 거르고 싶은 축만 토픽에, 나머지는 페이로드에**
- 🔴 가짓수가 무한한 값(시각·일련번호)을 토픽에 넣지 않는다
- 🔴 지금 하나뿐인 계층을 미리 파지 않는다. **계층은 나중에 앞에 붙일 수 있다**
- 형제를 같이 본다 — `status`(Last Will) · `alarm` 자리가 `shot` 축에서 나온다
- 구독 와일드카드: `+` 한 계층 / `#` 나머지 전부(**맨 끝에만**)

**페이로드 — JSON**
- 🔵 JSON 을 고른 이유는 **사람이 읽을 수 있어서.** 오늘 눈으로 검사한 것이 그 값어치.
  MessagePack·Protobuf 는 3~5배 작지만 못 읽는다. 느려지면 그때 바꾼다
- 🔴 `ISO = "%Y-%m-%dT%H:%M:%S+00:00"` — 타임존 없으면 받는 쪽이 자기 기준으로
  읽어서 **9시간 밀린다.** ADR 002 가 이미 UTC 로 정해놨다
- 🔴 `ensure_ascii=False` — 기본이 True 라 한글이 `가스` 로 나간다.
  **읽을 수 없는 로그는 없는 로그다**
- 🔴 빈 값은 키를 빼지 않고 `null` 을 적는다. "키가 없다"와 "값이 없다"는 다르다
- 🔵 `equipment_id` 가 토픽과 페이로드에 **둘 다** — 의도된 중복.
  저장하거나 로그에 남기면 **봉투는 사라지고 내용물만 남는다**

**🔴 자동 import 가 엉뚱한 걸 세 줄 넣었다**
```
from xmlrpc import client              ← "client" 이름만 보고 표준 라이브러리를 끌어왔다
from paho import mqtt                  ← 패키지다. Client 는 paho.mqtt.client 에 있다
from paho.mqtt import client as mqtt_client   ← mqtt 가 이미 쓰여서 이름이 바뀌었다
```
- `AttributeError: module 'paho.mqtt' has no attribute 'Client'`
- 🔴 `from xmlrpc import client` 가 제일 위험하다 — **에러가 안 난다.** 표준
  라이브러리에 진짜 있으니까. 지금은 지역변수가 덮어써서 안 터질 뿐이다
- 🔴 **자동 완성은 뜻을 모른다. 그 이름의 뭔가를 찾아줄 뿐이다. import 는 눈으로 본다**

**확인 — 보내봤다 ≠ 받았다**
```
터미널 B   docker exec shottrace-mosquitto mosquitto_sub -t "shottrace/#" -v
터미널 A   python services/simulator/replay.py --speed 3600 --limit 25
```
- 토픽 ✅ / `+00:00` ✅ / `"fail_reason": null` ✅ / parts 1개·2개 ✅ / 25건 ✅
- 🔴 `publish()` 는 토픽이 틀려도 JSON 이 깨져도 `loop_start()` 를 빼먹어도 에러가 없다

**관찰 두 가지**
- `59.52000045776367` — **CSV 원본이 그렇다.** float32 를 float64 로 옮긴 흔적.
  반올림하지 않는다. 파이프라인은 값을 나르고 **모양은 화면이 정한다** (ADR 008)
- 🔴 `parts` 배열 **순서가 매번 다르다.** `parts[0]` 을 LH 로 가정하면 조용히 틀린다.
  수집기는 `part_name` 으로 찾는다. **정렬해서 보내지 않는다** — 보장하면 기대게 된다

**한 일**
- QoS 1 · Last Will · retain · `on_connect`/`on_disconnect` · `KEEPALIVE`
- 페이로드에 **공정변수 24개** (`values`) · `cycle_time` 을 그 안으로 옮김
- `--equipment` 기본값 `S14` — **한 프로세스 = 한 설비**

**QoS — "정확히 한 번" 은 프로토콜이 아니라 설계로 얻는다**
```
0  많아야 한 번   잃어도 모른다          왕복 1
1  적어도 한 번   중복될 수 있다         왕복 2   ← 채택
2  정확히 한 번   느리다                 왕복 4
```
- 샷은 잃으면 안 되지만 **QoS 2 를 안 쓴다.** 중복을 우리가 막을 수 있기 때문.
  `shot` PK `(equipment_id, measured_at)` 로 upsert 하면 두 번 와도 행이 안 는다
- 🔵 9/2 에 정한 PK 가 또 회수됐다. 인덱스 · RPC 조인 · 복합 FK 에 이어 네 번째
- 🔴 **QoS 는 구간별이다.** 발행 1 + 구독 0 = 그 구간은 0. S04 에서 다시 나온다
- 🔴 **QoS 가 보장 못 하는 것** — 구독자가 없을 때 보낸 메시지는 그냥 사라진다.
  수집기가 죽어 있는 동안의 샷은 잃는다. 지속 세션은 S04 의 문제

**Last Will — 죽은 뒤에 말하는 법**
```
Ctrl+C          finally 돈다   ✅
프로세스 강제종료 안 돈다        ❌   ← 공장에서 흔한 건 이쪽
전원/랜선        안 돈다        ❌
```
- 연결할 때 브로커에 유언을 맡긴다. 말없이 사라지면 브로커가 대신 발행
- 🔴 **정상 종료하면 유언이 안 나간다.** `disconnect()` 는 인사하고 가는 것이라
  브로커가 유언을 버린다 → 그 경로는 `finally` 에서 **우리가 직접** offline 발행
- 실측: `taskkill /F` → 1초 만에 offline 도착
- ⚫ **1초인 이유는 keepalive 가 아니다.** 프로세스가 죽으면 OS 가 TCP 를 닫아
  브로커가 즉시 안다. `keepalive` 는 **TCP 를 닫아줄 사람이 없는 경우**(랜선·정전)용.
  기본 60초는 공장에 느려서 `KEEPALIVE = 15`

**retain — 상태에는 켜고 사건에는 끈다**
```
상태 state   지금 살아있나 · 현재 온도    ✅ 최신 하나가 곧 진실
사건 event   샷 · 알람                    ❌ 하나하나가 다 의미
```
- 🔴 `shot` 에 켜면 새 구독자가 **옛날 샷을 방금 온 샷으로 오해**한다
- 실측: 구독을 새로 켜자마자 직전 실행의 `{"state":"offline"}` 이 즉시 왔다
- 🔵 S05 실시간 화면이 **켜지자마자** 가동 상태를 표시할 수 있는 근거
- ⚫ 수요일에 `shot` 과 `status` 를 다른 토픽으로 나눈 값어치가 여기서 나왔다.
  한 토픽에 섞였으면 retain 을 켤 수도 끌 수도 없다

**재연결 — 조용히 끊기는 것을 막는다**
- paho 는 알아서 재연결하지만 **말을 안 해준다.** 콜백으로 로그를 남긴다
- 🔵 `online` 발행을 `on_connect` 안에 두면 **최초 연결과 재연결이 같은 코드**를 탄다
- 🔴 재연결 뒤 `online` 을 다시 보내야 retain 된 `offline` 을 덮는다
- 🔴 `on_connect` 는 **실패해도 불린다.** `reason_code != 0` 을 안 보면
  연결 거부인데 "연결됨" 이라고 찍는다
- ⚫ 지수 백오프(1→2→4→…120초)는 thundering herd 방지. 기본값 그대로 쓴다

**🔴 연결은 비동기다 — 첫 시도에서 순서가 틀렸다**
```
틀림   shot → status online      구독자에겐 "죽은 설비가 샷을 보냈다"
맞음   status online → shot
```
- `connect()` 가 돌아와도 **CONNACK 전**이다. `on_connect` 는 그게 와야 불린다
- `client.is_connected()` 로 최대 5초 기다린 뒤 재생을 시작한다
- ⚫ S04 수집기에서 그대로 필요한 패턴

**🔴 한 연결 = 한 유언 = 한 설비**
- MQTT 는 연결당 유언이 하나뿐이라 설비 3대를 한 프로세스로 흉내낼 수 없다
- 실제 공장도 설비 하나 = 클라이언트 하나. **모델을 현실에 맞췄다**
- `--equipment` 기본값 `S14`. 3대를 돌리려면 터미널 3개
- 데이터가 결정을 쉽게 해줬다 — S14 2,624샷 / S01·S12 각 1샷
