## 무엇을 정했나

| 질문 | 결정 |
|---|---|
| 정의 | **가동률** = 가동 ÷ (가동 + 셋업 + 계획 외 정지) · **성능** = 샷 수 × 표준 사이클타임 ÷ 가동 (100% 상한) · **품질** = 양품 ÷ 전체 |
| 셋업(금형 교체)은 | **손실** — 계획 정지가 아니다 (020) |
| 단위 | **LOT** — 부하 시간 = LOT 구간 (+ 한 사이클 · 022) |
| 성능의 횟수 | **샷 수** — 부품 수가 아니다 (패밀리 금형) |
| 표준 사이클타임 | **`product.std_cycle_sec`** · 처음 값은 **실측 중앙값 (임시)** |
| 품질의 원천 | **`shot_part`(설비의 판정)** — 현장의 "확정 실적" 과 다르다 |
| 어디서 계산하나 | **재료는 View(`lot_oee_input`), 계산은 순수함수(`computeOee`)** |
| 계산할 수 없을 때 | **null** — 0% 가 아니다 (분모 0 · 표준 없음) |

## 왜

### ① 셋업은 손실이다 — 현장 피드백으로 고쳤다

017 에서 금형 교체를 `planned = true`(계획 정지)로 넣었다. 계획 정지는 가동률의 분모에서 빠지므로
가동률이 실제보다 높게 나온다. 현장 MES 개발자 피드백(10/22)과 OEE 교과서(6대 로스) 모두 **셋업은 줄여야 할
손실**이다. OEE 를 만들기 **전에** 발견해 020 에서 고쳤다. 값 하나지만 왜를 남기려고 마이그레이션으로 했다.

### ② 100% 상한은 버그를 숨긴다 — 성능은 샷 수로, 자르기 전 값도 꺼낸다

S14 는 패밀리 금형이라 한 샷에 부품 둘(ADR 005). 성능에 부품 수를 넣으면 200% 가 100% 로 잘리고,
진짜로 느려져도(133%) 여전히 100% 다. 숫자가 "아주 잘 돌았다" 로 보인다.
그래서 **샷 수**로 계산하고 `performanceRaw`(자르기 전)를 같이 돌려준다. 화면은 110% 를 넘으면 ⚠ 를 붙인다.
LOT 은 제품 하나의 것이라 그 제품의 부품 수 = 샷 수 — View 는 LOT 단위로 세서 두 배가 되지 않는다.

### ③ LOT 경계는 조인용 — 일한 시간은 한 사이클 더 길다 (022)

`performanceRaw` 를 꺼내자 샷 1개짜리 LOT 이 **6,686%** 로 나왔다. LOT 끝 = 마지막 샷 + 1초(ADR 006)라
구간은 1초인데 한 샷은 약 62초다. 마지막 샷의 사이클이 구간 밖으로 빠져 있다 — 짧은 LOT 일수록 크게 틀린다.
**경계는 조인에 맞으니 그대로 두고**, OEE 재료에서만 부하 시간에 표준 사이클 하나를 더했다.
결과 — 자르기 전 값이 전부 100% 이하가 됐다(1샷 LOT 98.5% · 41샷 LOT 102.5% → 100.0%).
**같은 경계도 무엇에 쓰나에 따라 맞기도 틀리기도 한다.**

### ④ 계산은 순수함수

`computeOee` 는 숫자만 받고 DB · 시계 · 화면을 보지 않는다. 그래서 DB 없이 경우를 넣어 확인했고
(택시 하루 68% · 샷 수 67% · 부품 수 실수 100%(raw 133%) · 안 돌린 날 null), 다음 주 Vitest 가 그대로 쓴다.
SQL 은 재료(분 · 샷 · 양품)만 주고 계산 규칙은 TS 한 곳에 있다 — 규칙이 바뀌어도 View 는 그대로다.
S04 수집기의 `to_shot_row(msg, now)`(시계를 밖에서 받기)와 같은 생각이다.

### ⑤ 표준 사이클타임 · 품질의 원천 — 현장과 다르게 고른 둘

- **표준**은 현장에서 라우팅(공정 순서표)에 적힌 약속된 값이다. 우리에겐 없어서 **실측 중앙값**을 임시 표준으로 넣었다
  (CN7 59.52초 · RG3 61.78초 — 10% ~ 90% 가 ±0.06초로 매우 고르다). 마스터 값이라 나중에 고칠 수 있다.
  NOT NULL 로 묶지 않았다 — 새 제품은 표준이 아직 없을 수 있고, 그때 OEE 는 null 이 정직하다
- **품질**은 현장이 확정 실적을 쓴다. 우리 장부(사람의 실적)는 시연용이라 거의 비어 있고, `shot_part` 에는
  5,314개 부품의 판정이 다 있으며 현황판도 이걸 센다(ADR 012). 그래서 설비의 판정을 쓴다

### ⑥ 결과가 보여주는 것

비가동 기록이 없어 **가동률은 전부 100%**. 대신 LOT 안의 기록 안 된 멈춤(샷 틈)은 **성능 손실**로 보인다
(RG3 10/22 · 10/23 성능 63 ~ 66%). OEE 교과서에서도 작은 멈춤은 성능 손실이다 — 숫자가 조용히 틀린 게 아니라
**맞는 칸에** 보인다. 열어둔 데모 LOT(10/07)은 OEE 1.3% — 열려 있는데 설비가 거의 안 돌았다는 정확한 값이다.

## 버린 대안

**① 성능을 부품 수로** — 현장 공식("생산수량")을 그대로 옮기는 것. 버린 이유 — 패밀리 금형에서 두 배가 되고 상한이 숨긴다.

**② 근무 시간표 기준 부하** — 하루 · 교대 단위 OEE 의 정석. 버린 이유 — 근무 시간표가 없다. 우리 단위는 원래 LOT 이다.

**③ LOT 경계(`ended_at`)를 마지막 샷 + 한 사이클로 바꾸기** — 한 곳만 고치면 된다. 버린 이유 — 경계는 조인용이다.
바꾸면 다음 LOT 의 첫 샷이 앞 LOT 에 붙을 수 있다(ADR 006). 일한 시간을 셀 때만 더한다.

**④ 계산을 SQL View 안에서 끝내기** — 화면이 숫자만 꺼내면 된다(ADR 008 의 "집계는 DB 에서"). 버린 이유 —
비율 셋과 상한 · null 규칙은 **도메인 로직**이라 테스트하기 쉬운 순수함수가 낫다. 집계(합 · 개수)는 DB 가, 규칙은 TS 가.

**⑤ 표준 사이클타임을 평균으로** — 버린 이유 — 교체 직후처럼 튀는 값(최대 64초)에 끌려간다. 중앙값이 덜 흔들린다.

**⑥ 샷 틈을 자동으로 비가동으로 잡아 가동률에 넣기** — 가동률이 현실적이 된다. 버린 이유 — 사유가 없고 기준(몇 분)이 없다
(ADR 015). 기록 안 된 멈춤은 성능에 보이는 쪽이 정직하다. 찾아 알려주는 일은 뒤로 → **찾아 보여주고 사유는 사람이 고르는 방식**으로 [ADR 019](019-미입력-정지.md) (10/26).

## 🔴 따라오는 것

- **상한(100% 자르기)이 있는 지표는 자르기 전 값을 같이 꺼낸다**
- **분모가 0 이거나 기준이 없으면 null** — 0% 는 거짓말
- **단위를 맞춘다** — 표준은 초, 가동은 분 (`/ 60`). 다르면 에러 없이 60배 틀린다
- **열어둔 데모 LOT 은 닫는다** — 시연이 끝나면 `scripts/demo/demo_lot.sql`
- **`CREATE OR REPLACE VIEW` 는 전체를 다시 적는다** — 무엇이 바뀌었는지 머리 주석에 꼭 (022)

## 남은 것

- **설비별 · 일별 OEE** — 지금은 LOT 별만. 근무 시간표가 생기면
- **표준 사이클타임을 admin 이 고치는 화면** — 지금은 SQL 로만
- **품질을 확정 실적으로** — 장부에 실제 실적이 쌓이면 현장 방식으로 옮길지
