# 002. TimeStamp를 UTC로 해석하고 timestamptz로 저장

- **상태**: 채택
- **날짜**: 2026-09-01
- **관련 모듈**: M02 · M05 · M17

## 무엇을 정했나

KAMP 원본 CSV의 `TimeStamp` 컬럼을 **UTC로 해석**하고, DB에는 `timestamptz`
타입으로 저장한다. 화면에 표시할 때 KST로 변환한다.

## 왜

CSV에는 타임존 정보가 없다. `"2020-10-16 04:57:47"` 이 한국 시각인지 UTC인지
데이터만 봐서는 알 수 없어서, 시간대별 생산량 분포로 판단했다.

```
 원본시  →  KST      샷 수
  00     →  09시      715
  01     →  10시      998
  02     →  11시      918
  03     →  12시      840   ← 점심시간에 감소
  04     →  13시     1012
  05     →  14시     1245
  06     →  15시     1022
  07     →  16시      934
  08     →  17시      108   ← 퇴근
  09~22  →  18~07시     0   ← 생산 없음
  23     →  08시      204   ← 출근

  0~8시 합계  7,792건 / 9~23시 합계  204건
```

근거 세 가지.

1. **근무시간이 맞는다.** UTC 23~08시를 KST로 옮기면 08:00~17:00이고,
   한국 제조업 주간 1교대와 정확히 일치한다.
2. **점심시간이 보인다.** KST 12시에만 생산량이 918 → 840으로 꺼진다.
   앞뒤 시간대보다 낮은 건 이 구간뿐이다.
3. **KST로 가정하면 말이 안 된다.** 자정~08시에만 생산하고 주간에는
   3주 내내 한 건도 없었다는 뜻이 되는데, 현실적이지 않다.

`timestamptz` 를 고른 이유는 따로 있다. M17에서 배속 재생을 하면 "이벤트가
일어난 시각"과 "시스템이 받은 시각"이 6년 차이가 난다. 타임존 없는
`timestamp` 로 두면 서버 타임존(Vercel은 UTC, 로컬은 KST)에 따라 값이
달라져서 LOT 시간 구간 조인이 어긋난다.

## 버린 대안

**① `timestamp` (타임존 없음)**
저장이 단순하다. 버린 이유 — 서버 타임존에 휘둘린다. 로컬에서 맞던 조인이
Vercel에 올리면 9시간 틀어진다.

**② KST로 가정하고 저장**
"한국 공장 데이터니까 한국 시각이겠지"가 자연스러운 추측이었다.
버린 이유 — 위 분포로 반증됐다. 추측으로 갔으면 LOT 날짜 경계가 9시간
밀려서 25개 LOT의 묶음 자체가 달라졌을 것이다.

## 결과로 따라오는 것

- ETL에서 `TimeStamp` 를 UTC로 명시해 파싱한다
- 화면 표시는 KST로 변환한다 (M13 포맷 함수에서 한 곳으로)
- `PART_FACT_PLAN_DATE` 는 별개다 — 시각 부분이 전 행 동일해서 날짜만 쓴다
