# 013. 인증과 인가 — 입구는 친절하게, 문지기는 RLS

- **상태**: 채택
- **날짜**: 2026-10-16 (10-19 멱등 · 전수 점검 반영)
- **관련 파일**: `apps/web/lib/supabase/session.ts` · `apps/web/lib/supabase/client.ts`
  · `apps/web/proxy.ts` · `apps/web/app/login/actions.ts` · `apps/web/app/records/actions.ts`
  · `db/migrations/011_roles.sql` · `db/migrations/012_production_record.sql` · `db/migrations/013_request_id.sql`
  · `scripts/verify/rls_write.py` · `scripts/verify/rls_matrix.py`
- **관련 ADR**: [008](008-집계-위치.md) · [012](012-실시간-갱신.md)

## 무엇을 정했나

| 질문 | 결정 |
|---|---|
| 세션은 어디에 | **쿠키.** `@supabase/ssr` · 서버 클라이언트는 **요청마다** 새로 |
| 비로그인은 | **아무것도 못 본다.** 포트폴리오는 공개 **viewer 데모 계정**으로 |
| 역할은 어디에 | **테이블(`user_role`).** 토큰 · `user_metadata` 가 아니다 |
| 누가 막나 | **RLS.** proxy 는 안내만 한다 |
| 실적 쓰기는 | **worker · admin 만 INSERT.** UPDATE · DELETE 정책은 **없다** |
| 입력 검사는 | **서버의 Zod.** 브라우저 `required` 는 편의, DB `CHECK` 는 마지막 방어선 |
| 같은 제출이 두 번 오면 | **번호표(`request_id`) + `UNIQUE`.** 두 번째는 23505 → "이미 저장됐다" |

**인증(누구냐)과 인가(뭘 해도 되냐)를 한 ADR 로 묶는다.** 세션을 쿠키에 두지 않으면
RLS 가 "그 사람" 을 모르고, RLS 가 없으면 로그인은 장식이다. 하나를 바꾸면 나머지가 흔들린다.

## 왜

### ① 세션은 쿠키에 — 우리 화면은 서버가 그린다

```
쿠키           요청마다 자동으로 간다   서버가 본다
localStorage   요청에 안 실린다         서버는 모른다
```

`supabase-js` 의 브라우저 기본값은 localStorage 라 서버 컴포넌트가 "누가 보는지" 를 모른다.
🔴 신분이 들어간 클라이언트를 **싱글턴으로 두면 다른 사람의 신분이 섞인다.** 에러 없이.
그래서 `createSessionClient()` 는 함수다. 브라우저는 그 브라우저의 주인 한 사람뿐이라
`client.ts` 는 하나로 충분하다 — **싱글턴이 위험한지는 몇 사람이 같이 쓰느냐로 정해진다.**

서버에서는 `getSession` 이 아니라 `getUser` 를 쓴다. 앞의 것은 쿠키를 그냥 믿는다.

### ② 비로그인 차단 + 공개 데모 계정

읽기를 열어두면 인가의 절반이 없다. 공장의 생산·불량 데이터는 사내 비밀이 기본이다.
면접관에게는 로그인 화면에 적어둔 **viewer 계정** 하나를 준다 — "읽기만 된다" 를 직접 본다.

🔴 이 계정의 비밀번호는 공개다. **viewer 는 끝까지 읽기 전용이어야 한다.**
쓰기 권한이 붙는 순간 공개된 열쇠가 된다.

### ③ 역할은 테이블에

```
토큰(app_metadata)   빠르다 · 바꿔도 토큰이 만료될 때까지(최대 1시간) 옛 역할
테이블(user_role)    조금 느리다 · 바꾸면 즉시
```

MES 는 퇴사·이동에서 **권한 회수가 즉시**여야 한다. `user_metadata` 는 사용자가 스스로
고칠 수 있어서 권한에 쓸 수 없다.

`app_role()` 은 **`SECURITY DEFINER`** 다. "관리자는 명단을 본다" 정책이 명단을 읽으면
무한 재귀가 된다. ADR 008 이 View 에 `security_invoker` 를 건 것과 **정반대 방향**이라
창구를 좁혔다 — 인자를 안 받고 `auth.uid()` 하나만, `search_path = ''`.
정책 안에서는 `(SELECT app_role())` 로 감싸 **쿼리마다 한 번만** 부른다.

### ④ proxy 는 입구, RLS 는 문지기

proxy 는 토큰을 갈아주고 비로그인을 `/login` 으로 보낸다. 친절하지만 **막지는 않는다**
(Next 문서도 같은 말을 한다). API 를 직접 부르면 proxy 를 안 거친다.

```
anon 키로 API 직접 호출   →  []   (plant_summary 는 0 인 1행)
명단에서 뺀 viewer        →  proxy 통과 · 화면은 0
```

`plant_summary` 의 0 은 ADR 008 의 `security_invoker` 가 **처음으로 실제로 막은** 증거다.

### ⑤ 실적은 볼펜 장부 — 고치지 않는다

제조 기록은 감사 대상이다. 틀리면 지우지 않고 취소하고 다시 쓴다.
**"수정 불가" 를 조심해서 지키지 않고 구조로 막는다** — UPDATE · DELETE 정책을 만들지 않는다.
정책이 없는 동작은 RLS 가 전부 막는다. `updated_at` 칼럼도 없다.
`recorded_by` FK 에는 `CASCADE` 가 없다. 명단은 사람과 같이 지워져도 되지만 장부는 남아야 한다.

`WITH CHECK` 에 조건이 둘이다.
```
(SELECT app_role()) IN ('worker', 'admin')   역할
recorded_by = (SELECT auth.uid())            🔴 DEFAULT 는 값을 안 보냈을 때만 채운다
```
두 번째가 없으면 worker 가 `recorded_by` 에 남의 id 를 실어 **남의 이름으로** 쓸 수 있다.

### ⑥ 막히는 소리가 다르다

```
SELECT    USING 에 걸림        조용히 0 rows
INSERT    WITH CHECK 에 걸림   🔴 42501 new row violates row-level security policy
UPDATE    정책 없음             조용히 0행
DELETE    정책 없음             조용히 0행
```

화면은 `42501` 을 "실적 입력 권한이 없어요" 로 바꿔 보여주고, 그 밖의 에러는 사람에게 짧게
· 로그에는 원본을 남긴다.

### ⑦ 검사는 세 겹

```
브라우저   required · min        안내문 — 개발자 도구로 지워진다
서버       Zod (actions.ts)      검문소 — 사람 말로 돌려준다
DB         CHECK · RLS           마지막 방어선 — 앱을 안 거쳐도 막는다
```

🔴 `FormData` 의 값은 전부 글자다. `z.coerce.number()` 로 바꾸고, 빈칸 `""` 은 조용히 0 이 된다
(불량 빈칸 = 0 이라 받아들였다).

### ⑧ 같은 제출은 한 줄만 — 번호표와 UNIQUE

버튼 잠금은 줄여줄 뿐이다. 가장 흔한 중복은 **저장은 됐는데 응답만 못 받아 다시 누르는** 경우라서
서버에는 요청이 두 번 온다. 내용(양품 12 · 불량 1)으로는 가릴 수 없다 — 진짜로 두 번 만들었을 수도 있다.

```
page.tsx 가 그릴 때마다   crypto.randomUUID() → hidden 칸
성공                     revalidatePath → 다시 그림 → 새 번호표
실패 (Zod · 권한)         다시 안 그림 → 같은 번호표
두 번 눌림                같은 번호표 두 번 → UNIQUE → 23505 → ok: true "이미 저장됐어요"
```

번호표 교체 시점을 따로 관리하지 않는다. 이미 있던 `revalidatePath` 가 그 시점이다.
🔴 `request_id` 에 **`DEFAULT gen_random_uuid()` 를 두지 않았다.** 앱이 번호표를 깜빡하면
DB 가 새 번호를 만들어 두 번 누른 제출이 서로 다른 번호가 된다 — 아무것도 못 막으면서 에러도 없다.
`NOT NULL` 만 두면 깜빡한 순간 에러가 난다.

### ⑨ 전수 점검 — 도면과 실제가 일치하는가

```
도면 (pg_policies)   테이블 7개 모두 RLS 켜짐 · 정책 8개 = SELECT 7 + INSERT 1
                     UPDATE · DELETE · ALL 정책 0개
실제 (rls_matrix)    역할 5 (비로그인 · 명단없음 · viewer · worker · admin)
                     × 테이블 7 · View 4 · 함수 2  → 전부 예상대로
```

- 비로그인 · 명단없음은 모든 테이블 · View · 함수에서 **0** (`plant_summary` 는 0 인 1행)
- `user_role` 은 본인 한 줄, admin 만 전부
- INSERT 빈 행 — 42501 이 34칸, **23502 가 2칸**(production_record × worker · admin).
  두 칸만 RLS 를 통과하고 NOT NULL 이 잡았다 = 정책이 정확히 그 두 칸만 열었다
- UPDATE(같은 값으로 덮기) — 35칸 전부 0행
- **DELETE 는 두드리지 않았다.** 뚫려 있으면 진짜로 지워진다. 도면에 DELETE 정책이 0개인 것으로 증명한다
- 🔵 함수도 문이다. Supabase 는 public 함수를 `/rpc` 로 연다. `app_role()` 은 비로그인도 부를 수 있지만
  인자 없이 "나" 하나만 돌려주므로 비로그인에게는 `null` 이다

## 버린 대안

**① 비로그인에게 읽기를 열어둔다**
데모가 가장 쉽다. 버린 이유 — 인가가 쓰기에만 있으면 RLS 의 절반을 안 보여준다.
데모 계정 하나로 같은 편의를 얻는다.

**② 역할을 JWT(`app_metadata`)에 넣는다**
정책이 테이블을 안 읽어서 빠르고 재귀 문제도 없다. 버린 이유 — 역할을 바꿔도
토큰이 만료될 때까지 옛 권한이 산다. 이 프로젝트 규모에서 명단 조회 비용은
`(SELECT …)` 로 쿼리당 한 번이라 무시할 만하다.

**③ proxy 에서 역할까지 검사한다**
화면 단위로 막으면 빨리 튕겨낼 수 있다. 버린 이유 — 막는 곳이 둘이 되면 둘이 어긋난다.
API 직접 호출은 어차피 proxy 를 안 거친다. proxy 는 로그인 여부만 보고, 역할은 RLS 한 곳에서.

**④ 실적 수정을 UPDATE 로 허용하고 이력 테이블을 둔다**
흔한 방식이다. 버린 이유 — 트리거로 이력을 남기면 "고칠 수 있다" 가 기본이 되고,
이력이 빠지는 경로(트리거 비활성화 등)를 따로 막아야 한다. 고칠 수 없게 두고
**취소 + 재등록**(트랜잭션)으로 가는 쪽이 감사에 단순하다.

**⑤ 검사를 Zod 하나로 끝낸다 (DB CHECK 없이)**
버린 이유 — DB 에 쓰는 길이 앱 하나가 아니다(수집기 · SQL Editor · 앞으로의 스크립트).
Zod 는 친절하게, DB 는 끝까지.

## 🔴 따라오는 것

- **SQL Editor 는 RLS 를 안 거친다.** 거기서 보이는 것 ≠ 사용자가 보는 것.
  확인은 항상 **역할별로 실제 로그인해서** — `scripts/verify/rls_write.py`
- **마이그레이션을 걸면 타입도 다시 뽑는다** (`supabase gen types`). 011 때 빠뜨려서
  012 에서야 발견했다
- **DB 와 코드를 같이 바꿀 때는 양쪽에서 도는 쪽을 먼저 배포**한다. 정책을 먼저 좁히면
  옛 코드가 빈 화면이 된다
- **service_role 은 RLS 를 건너뛴다.** 수집기와 시험 행 정리에만 쓴다. 브라우저에는 절대 안 간다
- **IDENTITY 번호에는 구멍이 생긴다.** 막힌 INSERT 도 번호를 가져간다 — 개수는 `COUNT` 로
- **재귀 고리가 함수 속에 있으면 42P17 이 아니라 54001 이다.** `app_role()` 을 일부러 `SECURITY INVOKER`
  로 바꿔보니 `infinite recursion detected` 가 아니라 `stack depth limit exceeded` 가 났다. 정책이 자기
  테이블을 직접 가리키면 Postgres 가 미리 알아채지만, 함수 본문 속 SELECT 는 실행해봐야 보인다.
  🔴 힌트(`max_stack_depth` 를 늘려라)를 따르면 안 된다 — 무한이라 늦게 쓰러질 뿐이다. 고리를 끊는다
- **React 19 는 폼 action 뒤에 입력칸을 리셋한다.** 실패 쪽지에 입력값을 담아 `defaultValue` 로
  돌려준다. 🔴 `select` 의 `defaultValue` 는 mount 때만 읽혀서 `key` 로 새로 그린다
