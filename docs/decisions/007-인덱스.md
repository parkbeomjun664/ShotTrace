# 007. 인덱스 3개를 걸고, FK 컬럼에는 걸지 않는다

- **상태**: 채택
- **날짜**: 2026-09-09
- **관련 모듈**: M06 ★
- **증거**: [docs/evidence/003-indexes-explain.md](../evidence/003-indexes-explain.md)

## 무엇을 정했나

`003_indexes.sql` 로 인덱스 3개를 추가한다. PK·UNIQUE 가 자동으로 만든 7개에 더해 총 10개.

| 인덱스 | 대상 | 담당 쿼리 |
|---|---|---|
| `idx_shot_part_lot_lookup` | `shot_part (equipment_id, product_id, measured_at)` | LOT 상세 시간 구간 조인 |
| `idx_production_lot_started_at` | `production_lot (started_at DESC)` | LOT 목록 정렬 |
| `idx_shot_part_defect` | `shot_part (fail_reason) WHERE pass_or_fail = 'N'` | 불량 파레토 |

**FK 컬럼에는 걸지 않는다** — `production_lot.equip_cd` · `production_lot.product_id`.

## 왜

### 컬럼 순서 — 등호 먼저, 범위 나중

`getLotShots()` 는 이렇게 조건을 건다.

```
equipment_id = ?      등호
product_id   = ?      등호
measured_at 범위      범위
```

기존 `UNIQUE (equipment_id, measured_at, product_id)` 는 **범위가 가운데 끼어 있어서**
`product_id` 를 인덱스로 좁히지 못한다. 범위 조건 다음 컬럼부터는 정렬이 끊기기 때문이다.

이 사실이 실측으로 확인됐다. `product_id` 조건을 뺀 쿼리에서 **옵티마이저가 새 인덱스가
아니라 옛 UNIQUE 인덱스를 골랐다.** `(equipment_id, product_id, measured_at)` 의
가운데 칸이 비면 그 뒤를 못 쓴다 — 왼쪽 접두사 규칙이다.

두 인덱스는 서로 다른 쿼리를 담당한다. 옵티마이저가 쿼리마다 고른다.

### 측정 결과

`shot_part` 5,232행 · LOT `S14-20201103-CN7LH` 463행 조회.

| | 스캔 방법 | cost | 실행 시간 |
|---|---|---|---|
| 인덱스 사용 | `Index Scan` | 0.28..66.27 | **2.442 ms** |
| 인덱스 끔 | `Seq Scan` | 0.00..211.64 | 10.986 ms |

`Seq Scan` 의 **`Rows Removed by Filter: 4769`** 가 `5,232 − 463` 과 정확히 일치한다.
필요한 것의 11배를 읽고 버린다. cost 3.2배, 실행 시간 4.5배.

### 부분 인덱스

불량은 5,232건 중 **60건(1.15%)** 뿐이다. 전체를 색인할 이유가 없다.

```
전체 인덱스   5,232 항목
부분 인덱스      60 항목      87배 작다
```

선택도가 낮을수록 부분 인덱스의 이점이 크다. 절반이 불량이었다면 의미가 없었을 것이다.

### 지금 걸어야 하는 이유

현재 5,232행은 인덱스 없이도 빠르다. 그래도 지금 거는 이유는 둘이다.

- 10월에 시뮬레이터가 돌면 수만 행, 1~2월 성능 심화에서 50만 행이 된다.
- **지금 EXPLAIN 으로 증명해두는 것**과 데이터가 커진 뒤 급하게 거는 것은 다르다.
  근거가 남는다.

## 버린 대안

- **기존 UNIQUE 로 충분하다** — 인덱스를 추가하지 않는 선택. 실측하니 `product_id` 를
  못 좁혀 **926행을 읽고 절반을 버린다.** LH·RH가 같은 시간대를 공유하기 때문이다
  (ADR 005). 정확성은 필터가 보장하지만 읽는 양이 두 배다.

- **FK 컬럼에 전부 인덱스** — 흔한 관행이지만 지금은 근거가 없다.
  `production_lot` 은 25행이고, **설비나 제품으로 LOT을 검색하는 쿼리가 화면에 없다.**
  인덱스는 쓰기를 느리게 하고 용량을 먹는다. 마스터 삭제가 생기는 S07(M23)에서
  필요해지면 그때 이유와 함께 추가한다.

- **데이터가 커진 뒤에 걸기** — 나중에 걸어도 동작은 같다. 하지만 그때는
  "느려서 급하게 걸었다"가 되고, 지금 하면 "쿼리를 보고 설계했다"가 된다.
  **같은 결과라도 근거가 남는지가 다르다.**

## 남은 관찰

`idx_production_lot_started_at` 은 **아직 쓰이지 않는다.** 25행짜리 테이블이라
`Seq Scan` + `Sort`(cost 1.89)가 인덱스를 거치는 것보다 싸다.

낭비는 아니다. LOT은 계속 쌓이고, 행이 늘면 옵티마이저가 스스로 판단을 바꾼다.
**"인덱스를 걸었다"와 "인덱스를 쓴다"는 다르다** — 이것도 실측으로 확인했다.

`idx_shot_part_defect` 는 품질 화면(S01)을 만든 뒤 측정한다.
