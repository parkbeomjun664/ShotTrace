# 012. 실시간 갱신 — 알림은 신호, 값은 서버가 다시 읽는다

- **상태**: 채택
- **날짜**: 2026-10-09
- **관련 모듈**: M18
- **관련 파일**: `apps/web/app/LiveRefresh.tsx` · `apps/web/lib/supabase/client.ts`
  · `db/migrations/010_live_summary.sql` · `services/simulator/replay.py`
  · `scripts/demo/demo_lot.sql`
- **관련 ADR**: [008](008-집계-위치.md) · [009](009-설비-메시지-계약.md)
  · [010](010-시간의-설계.md) · [011](011-수집기-구동-위치.md)

## 무엇을 정했나

| 질문 | 결정 |
|---|---|
| 알림을 어떻게 쓰나 | **신호로만.** 값은 서버가 다시 읽는다 |
| 집계를 어디서 하나 | **`shot_part` 원본에서.** `production_lot` 저장값을 안 본다 |
| 얼마나 자주 갱신하나 | **1초 throttle.** debounce 가 아니다 |
| 캐시는 | **`revalidate = 0`.** 실시간 화면에는 캐시를 안 켠다 |
| 무엇을 발행 명단에 | **`shot_part` 하나.** 명단은 적을수록 좋다 |
| 데모 데이터는 | **`--live`** 로 "지금부터" 1배속 + **진행 중 LOT** 하나 |

**이 여섯이 한 덩어리다.** 하나를 뒤집으면 나머지가 같이 무너진다.

## 왜

### 네 개처럼 보이지만 한 질문이었다

"알림을 신호로만 쓴다" 를 뒤집으면 — 집계가 브라우저로 넘어오고(②), throttle 이
의미를 잃고(③), 놓친 알림을 세야 한다(복구). **서로를 떠받치고 있으므로 한 ADR 이다.**
ADR 010 에서 가상 시계와 진행 중 LOT 을 하나로 묶은 것과 같은 판단이다.

### ① 알림 ≠ 데이터

```
payload 로 숫자를 고친다   → 수율 계산이 브라우저로 넘어온다. ADR 008 을 뒤집는 것
payload 를 신호로만 쓴다   → 집계는 계속 DB 가 한다
```

**이벤트는 타이밍만 알려준다. 값은 언제나 DB 에서 온다.**

🔵 이 선택이 **함정 셋을 미리 지웠다.**

- **Realtime 이 View 를 못 본다** — 문제가 아니게 된다. View 는 구독하는 게 아니라
  **다시 조회하는 것**이다
- **`REPLICA IDENTITY FULL` 이 필요 없다** — 바뀌기 전 값을 쓰지 않으니까
- **재연결 복구가 한 줄이다** — "다시 조회" 가 유일한 갱신 경로라서,
  `SUBSCRIBED` 일 때 한 번 받아오면 **몇 개를 놓쳤는지 셀 필요가 없다**

### ② 집계는 저장값이 아니라 원본에서

수집기는 `shot_part` 에 쓰는데 현황판은 `production_lot` 의 저장 컬럼을 읽고 있었다.
**알림이 완벽하게 와도 다시 조회한 값이 같다.** 미결이던 "저장 집계" 가 실시간의
**전제조건으로 승격**했다 — 실시간은 "미결을 나중에" 가 안 되는 기능이다.

🔴 **바꾸기 전에 먼저 세어봤다.**

```
production_lot 합   5,232
shot_part COUNT     5,232 · 양품 5,172 · 불량 60
```

**두 집계가 정확히 일치했다.** 숫자가 안 달라진 것이 교체가 안전했다는 증거다.
미할당 생산도 0건이라 미결 하나가 같이 닫혔다.

🔴 수량(`shot_part`)과 LOT 개수(`production_lot`)는 **입도가 다르다.** 한 번에 조인하면
행이 곱해지고(fan-out) **에러 없이 생산량만 부푼다.** 각각 설비당 1행으로 접은 뒤 붙인다.

### ③ throttle 1초 — debounce 가 아니다

```
60배속 · 설비 3대   shot_part INSERT 초당 6건
현황판은 View 2개   → 초당 12 왕복 · 탭 3개면 36
```

```
debounce   마지막 이벤트 후 조용해지면 실행   🔴 생산 중에는 영원히 안 돈다
throttle   아무리 와도 1초에 한 번           ✅ 꾸준히 갱신된다
```

**debounce 는 검색창용이다.** 실시간 화면에서 "조용해질 때" 는 오지 않는다.
사람 눈에는 1초면 충분히 "살아 있다" 로 보인다. 수율이 초당 6번 바뀔 이유가 없다.

### ④ 캐시를 켜둔 채로는 실시간이 아니다

`revalidate = 60` 이면 `router.refresh()` 를 불러도 **묵은 화면이 올 수 있다.**
🔴 알림도 오고 새로고침도 되는데 **숫자만 안 바뀐다.** 에러는 나지 않는다.

### ⑤ 데모는 `--live` 로 "지금부터"

재생기는 원본 `measured_at` 을 보낸다. 이미 있는 행을 때리므로 `upsert` 가 **UPDATE** 가
되고 숫자가 안 움직인다. 🔵 **고장이 아니라 멱등성이다** — 9월에 일부러 그렇게 만들었고
그 판단은 지금도 맞다. MQTT 는 QoS 1 이라 **중복 수신이 정상 동작**이다(ADR 009).

🔵 **쉬운 길은 ADR 010 이 이미 다 막아뒀다.** 벽시계로 덮기 · 오늘 날짜로 옮기기 ·
배속 압축이 전부 거기 "버린 대안" 에 있다. `--live` 는 셋을 다 피한다.

```
1배속          cycle_time 59.52초 와 샷 간격 60초가 서로를 부정하지 않는다
지금부터       미래 시각이 안 생긴다
새 LOT 을 연다 2020년 LOT 25개를 건드리지 않는다
```

🔴 시각을 옮길 때 **재생기와 같은 규칙을 써야 한다.** 순진하게 `원본 + (지금 − 첫 샷)` 으로
더하면 구멍에서 깨진다 — 재생기는 300초만 기다리는데 `measured_at` 은 3시간을 뛴다.
그래서 `to_live` 는 `wait_for` 를 **그대로 불러** 누적한 값을 시각에 쓴다.
**같은 규칙이 두 군데 필요하면 함수를 재사용한다. 복사하면 언젠가 어긋난다.**

🔵 덤 — 진행 중 LOT(`'infinity'`)과 `EXCLUDE` 제약이 **시연에서 처음으로 눈에 보인다.**
만들어두고 보여줄 데가 없던 기능이었다.

## 버린 대안

**① 폴링 (주기적으로 다시 묻기)**
가장 간단하고 Realtime 을 안 배워도 된다. 버린 이유 — **100번 물어 1번 건진다.**
간격을 줄이면 비용이 늘고, 늘리면 지연이 늘어 어느 쪽도 "실시간" 이 아니다.

**② payload 의 값으로 화면 숫자를 직접 고치기**
왕복이 0이라 가장 빠르다. 버린 이유 — **집계가 브라우저로 넘어온다.** ADR 008 에서
"집계는 DB" 로 정한 것을 뒤집는다. 그리고 끊긴 동안 놓친 알림을 복구할 방법이 없다.

**③ 현황판 전체를 client component 로**
구독과 렌더가 한곳에 모인다. 버린 이유 — **첫 화면이 서버에서 완성돼 오는 장점을 버린다.**
서버가 첫 데이터를 주고 작은 client 조각이 구독만 맡는 쪽이 싸다.

**④ debounce**
구현이 throttle 과 비슷하다. 버린 이유 — **생산이 계속되면 영원히 안 돈다.**

**⑤ 수집기가 `production_lot` 집계도 갱신**
저장 집계의 속도를 유지한다. 버린 이유 — 진실이 두 곳이 되고, `CHECK (pass + fail = total)`
때문에 세 컬럼을 한 번에 맞춰야 한다. **트랜잭션·동시성 이야기는 S07 칸에 이미 있다.**

**⑥ `shot` 도 발행 명단에 넣기**
LOT 상세가 `shot` 의 `cycle_time` 을 쓰니 자연스러워 보인다. 버린 이유 — **불필요하다.**
수집기는 항상 `shot` 과 `shot_part` 에 같이 쓰므로 `shot_part` 알림이 이미 온다.
알림을 받고 나서 RPC 를 다시 읽으니 **신호의 출처는 상관없다.** 명단은 적을수록 좋다.

**⑦ 데모 없이 MVP 점검하기 (받은 그대로 재생)**
할 일이 없다. 버린 이유 — **숫자가 안 움직여서 "살아 움직이는 화면" 을 보여줄 수 없다.**
알림이 온다는 것까지만 보이고, 그건 실시간처럼 보이는 화면이지 실시간이 아니다.

## 🔴 따라오는 것

- **발행 명단(`publication`)에 없으면 알림이 안 온다.** 구독은 `SUBSCRIBED` 가 되고
  **에러도 안 난다.** View 를 구독해도 증상이 똑같다 — 둘 다 조용하다
- **서버 컴포넌트는 구독할 수 없다.** WebSocket 은 브라우저가 붙든다 →
  `"use client"` 조각과 브라우저용 클라이언트(`lib/supabase/client.ts`)가 필요하다
- **`removeChannel` 을 안 하면 구독이 쌓인다.** 개발 중에는 React 가 일부러 두 번
  마운트하므로 바로 2배가 된다
- **`event: "*"` 로 받는다.** 수집기가 `upsert` 라 같은 샷이 UPDATE 로도 온다
- **저장 집계를 보는 화면이 아직 둘 남아 있다** — 품질 화면 헤더와 LOT 목록.
  S07 에서 `lot_summary` View 와 함께 정리한다
- **데모 데이터의 기준은 "2026년 이후"** 다. 원본은 2020-10 ~ 11 뿐이라 섞이지 않는다.
  치우는 순서는 `shot_part` → `shot` (FK)

## 남은 것

- **🔴 S06 에서 RLS 를 역할 기반으로 바꾸면 Realtime 도 같이 영향을 받는다.**
  구독은 `anon` 키로 나가고 **알림에도 RLS 가 적용된다.** `USING (true)` 를 좁히는
  순간 알림이 조용히 끊길 수 있다 — 그 주에 반드시 같이 확인한다
- **끊김을 어떻게 재현하나** — DevTools 의 Offline 은 **이미 열린 WebSocket 을 못 끊는다.**
  와이파이를 끄면 DB 도 같이 끊겨서 "끊긴 동안 데이터가 들어온 상황" 을 만들 수 없다
- **여러 탭·여러 사람이 동시에 볼 때의 비용** — 지금은 탭마다 구독과 조회가 따로 돈다
