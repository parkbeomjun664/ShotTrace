## 무엇을 정했나

| 질문 | 결정 |
|---|---|
| 취소를 어디에 남기나 | **별도 장부 `record_cancel`.** `production_record` 는 손대지 않는다 |
| 같은 줄을 두 번 취소하면 | **`record_cancel` 의 PK = 원래 줄 번호.** 두 번째는 23505 |
| 정정(취소 + 새 줄)은 | **plpgsql 함수 `correct_record()` 하나.** 부르는 한 번 = 트랜잭션 하나 |
| 그 함수의 권한은 | **`SECURITY INVOKER`.** 부른 사람의 RLS 그대로 |
| 합계는 무엇으로 | **`active_record` View** — 취소 장부에 없는 줄만 · `security_invoker` |
| upsert 는 어디에 | **기계의 사실(shot · shot_part)에만.** 사람의 기록은 INSERT + 23505 |
| 제약 이름은 | **직접 붙인다.** 이름 없는 여러 칼럼 CHECK 넷에 016 에서 붙였다 |

## 왜

### ① 정정은 두 동작이고, 하나만 들어가면 조용히 틀린다

```
취소만 들어감    생산량이 줄어든다 (21 을 만들었는데 0)
새 줄만 들어감   12 + 21 = 33 으로 부푼다
```

둘 다 에러가 없다. Server Action 에서 `insert` 를 두 번 부르면 요청 둘 = 트랜잭션 둘이라
사이에서 실패하면 반쪽이 남는다. 그래서 두 동작을 **DB 함수 하나**에 넣었다.

```
correct_record()
  ① 원래 줄 읽기 (RLS 를 거친다 · 없으면 RAISE P0002)
  ② record_cancel INSERT        ← 이미 취소됐으면 PK 가 23505
  ③ 새 줄 INSERT (같은 LOT)      ← 실패하면 ② 도 없던 일
  ④ 새 줄 번호
```

실측 — 0 + 0 으로 정정하면 ③ 이 `record_qty_positive`(23514)에 걸리고, 먼저 그은 빨간 줄도
남지 않았다. 새 줄과 빨간 줄의 `now()` 가 초 단위까지 같다 — 같은 트랜잭션이라는 증거다.

### ② 동시 정정은 트랜잭션으로 못 막는다 — 구조로 막는다

트랜잭션은 **반쪽**을 막지 **동시**를 막지 않는다. A 와 B 가 같은 줄을 동시에 정정하면 각자의
묶음은 완전해서 둘 다 들어간다. "읽고(취소됐나?) → 판단 → 쓰기" 사이의 틈이다.
번호표(request_id)도 못 막는다 — 서로 다른 제출이다.

```
잠그기 (SELECT … FOR UPDATE)   깜빡하면 뚫린다
구조 (PK)                      누가 어떤 길로 와도 막힌다   ← 채택
```

실측 — worker 둘을 출발선에 세워 같은 순간 정정: 성공 1 · 실패 1(23505 `record_cancel_pkey`).
두 번째는 첫 번째가 확정될 때까지 기다렸다가 거절됐다. 잠금 코드는 한 줄도 없다.
shot 의 PK(멱등) · LOT 의 EXCLUDE(겹침) · request_id 의 UNIQUE(중복 제출)와 같은 줄기다.

### ③ INVOKER — DEFINER 면 viewer 가 장부를 고친다

```
app_role()        DEFINER   정책 ↔ 함수 재귀를 끊으려고 일부러 RLS 를 건너뛴다 (ADR 013)
correct_record()  INVOKER   함수 안의 INSERT 가 부른 사람의 RLS 를 지난다
```

DEFINER 로 만들면 함수 안의 두 INSERT 가 만든 사람 권한으로 돌아 **공개 viewer 계정이 정정**한다.
같은 단어가 함수마다 정반대 이유로 쓰인다. 실측 — viewer 정정은 42501, 원래 줄은 멀쩡하다.
`recorded_by` · `canceled_by` 는 DEFAULT `auth.uid()` 가 채우는데, INVOKER 라서 그 값이 부른 사람이다.

### ④ 합계는 살아 있는 줄만 — View 하나로

원래 장부가 그대로 남으므로 "취소 안 된 줄만" 골라야 한다. 화면마다 조건을 쓰면 한 군데서
빠뜨린다. `active_record` 하나에 두고 모두가 그걸 읽는다 (ADR 008 의 "집계는 DB 에서").

🔴 View 의 칼럼은 타입 생성기가 전부 `| null` 로 적는다(Postgres 가 View 의 NOT NULL 을
추적하지 않는다). 원본이 NOT NULL 이라는 근거로 `overrideTypes<…, { merge: false }>()` 로 덮었다.

### ⑤ upsert 는 데이터의 성격으로 고른다 (M22)

```
shot (기계의 사실)     같은 샷은 내용도 같다 · QoS 1 은 "적어도 한 번" → ON CONFLICT DO UPDATE
장부 (사람의 기록)     덮어쓰기 = 고치기 → 누가 무엇을 고쳤는지 사라진다  → INSERT + 23505
```

같은 "이미 있으면" 문제를 둘로 푼다. `DO UPDATE` 는 조용히 덮어쓴다.

### ⑥ 제약 거부 실험 — 코드가 실수해도 DB 가 막는다 (M22)

service_role 로 RLS 를 건너뛰어 종류마다 하나씩 일부러 어겼다 — 9 / 9 막힘
(`docs/evidence/constraints-reject.md`). 겹치는 LOT 은 `lot_no_overlap` 이 23P01 로 거절했다.
지도로 보면 **없었을 때의 결과가 전부 에러가 아니라 조용히 틀린 숫자**다.

실험이 하나를 드러냈다. 여러 칼럼을 보는 CHECK 에 이름을 안 붙여서 `production_lot_check` ·
`_check1` 로 찍혔다 — 에러만 보고는 무엇을 어겼는지 모른다. 이번 주에 만든 012 도 그랬다.
016 에서 `lot_qty_sum` · `lot_time_order` · `record_qty_positive` · `part_fail_has_reason` 로 붙였다.

## 버린 대안

**① 원래 줄에 `canceled_at` 을 적는다 (UPDATE)**
가장 흔하고 합계도 `WHERE canceled_at IS NULL` 이면 된다. 버린 이유 — UPDATE 정책을 열어야 한다.
한 번 열면 취소 표시만이 아니라 수량을 고치는 길도 같이 열린다. ADR 013 의 볼펜 장부가 무너진다.

**② 빼기 줄(역분개) — `pass_qty = -12` 인 취소 줄**
회계가 실제로 쓰는 방식이고 그냥 더하면 합계가 맞는다. 버린 이유 — `pass_qty >= 0` 을 풀어야 한다.
그러면 실수로 넣은 -5 와 의도한 빼기 줄을 DB 가 구별하지 못한다. `cancels UNIQUE` 로 두 번 취소는
막을 수 있지만 음수 실수는 못 막는다.

**③ 정정을 Server Action 에서 insert 두 번으로**
코드가 익숙하고 RPC 가 필요 없다. 버린 이유 — 요청 둘 = 트랜잭션 둘. 사이에서 실패하면 반쪽이 남는다.

**④ 동시 정정을 `SELECT … FOR UPDATE` 로 막는다**
정석이다. 버린 이유 — 함수 안에서 잠그는 걸 깜빡하거나, 다른 길(스크립트 · 다른 RPC)로 취소하면 뚫린다.
PK 는 길을 가리지 않는다.

**⑤ 정정 함수를 `SECURITY DEFINER` 로**
RLS 를 신경 쓰지 않고 함수 안에서 역할을 직접 검사하면 된다. 버린 이유 — 검사를 함수마다 다시 써야 하고,
빠뜨리면 viewer 가 장부를 고친다. RLS 한 곳에서 막는 ADR 013 ③④ 의 방향과 어긋난다.

## 🔴 따라오는 것

- **취소를 취소할 수는 없다.** `record_cancel` 에도 UPDATE · DELETE 정책이 없다. 잘못 취소했으면 새 줄로 다시 적는다
- **함수 하나 = 트랜잭션 하나.** 두 동작이 함께여야 하면 RPC 로 묶는다. 화면에서 묶을 수 없다
- **`now()` 는 트랜잭션 시작 시각이다.** 한 함수 안에서 찍은 시각은 모두 같다
- **View 타입은 `| null`.** 덮어쓸 때는 원본이 NOT NULL 이라는 근거가 있어야 한다
- **제약에는 이름을 붙인다.** `ADD CONSTRAINT 이름 …` · `CONSTRAINT 이름 CHECK (…)`
- **새 테이블은 확인 스크립트 목록에도.** `rls_matrix.py` 의 TABLES · VIEWS

## 남은 것

- **새 줄의 `recorded_at` 은 정정한 시각이다.** 원래 생산 시각을 남겨야 하는지 — LOT 을 닫을 때의
  `ended_at` 문제(ADR 006 꼬리)와 함께 본다
- **정정 폼은 실패해도 값 유지가 없다** (저장 폼에는 있다 · ADR 013)
- **양품 · 불량 Zod 검사가 두 군데** (`RecordInput` · `CorrectInput`)
- **화면에서 23505 메시지("이미 저장된" · "이미 정정된")를 못 봤다** — 버튼이 잠겨 손으로 재현이 어렵다 → S08 Playwright
- **현황판 · LOT 집계는 아직 `production_record` 를 안 본다** — 지금 생산량은 shot_part 에서 센다(ADR 012).
  사람의 실적과 설비의 샷 수가 어긋날 때 무엇을 믿을지는 OEE(M24) 에서 정한다
