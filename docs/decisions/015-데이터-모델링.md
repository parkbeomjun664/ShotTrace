# 015. 데이터 모델링 — 같은 사실은 한 곳에, 마스터는 지우지 않는다

- **상태**: 채택
- **날짜**: 2026-10-22
- **관련 파일**: `db/migrations/017_downtime.sql` · `018_defect_code.sql` · `019_master_admin.sql`
  · `apps/web/app/downtime/` · `apps/web/app/master/` · `services/collector/collector.py`
  · `docs/schema.md` · `scripts/verify/constraints.py`
- **관련 ADR**: [001](001-시간구간-조인-구조.md) · [002](002-타임존.md) · [006](006-LOT-경계.md)
  · [009](009-설비-메시지-계약.md) · [013](013-인증과-인가.md) · [014](014-취소와-정정.md)

## 무엇을 정했나

| 질문 | 결정 |
|---|---|
| 비가동을 어떻게 적나 | **구간 한 줄** (시작 · 끝) — LOT 과 같은 모양, 겹침은 EXCLUDE |
| 비가동 사유는 | **명단(`downtime_reason`) + 코드** · 명단에 `planned`(계획 정지인가) |
| 누가 적나 | **사람** — 사유는 사람만 안다. 장부와 같은 규칙(worker·admin · 고치지 않음) |
| 진행 중 비가동은 | **이번엔 안 받는다** — 끝난 비가동만 (`downtime_not_future`) |
| 불량 사유는 | **글자 그대로 두고 명단(`defect_code`)만 붙인다** — 자연키 FK |
| 마스터를 지우면 | **지우지 않는다.** `active = false` (사용 중지) · admin 만 고친다 |
| 화면의 시각 입력 | **`+09:00` 을 붙여 읽는다** — `datetime-local` 에는 타임존이 없다 |

## 왜

### ① 같은 사실을 여러 곳에 적으면 언젠가 갈라진다

불량 사유 61줄이 `shot_part.fail_reason` 에 글자로 적혀 있다(가스 36 · 미성형 15 · 초기허용불량 10).
지금은 깨끗하지만 손 입력이 시작되면 "가스" · "가스 " · "GAS" 로 갈라지고 파레토의 1등이 조용히 바뀐다.
정규화(1NF ~ 3NF)는 이 증상에 붙인 이름이다. **한 곳에만 적고 나머지는 가리킨다.**

### ② 마스터와 트랜잭션은 다루는 법이 다르다

```
마스터 (메뉴판 — 무엇이 있나)        고칠 수 있다 (admin) · 지우지 않는다 (사용 중지)
트랜잭션 (주문서 — 무슨 일이 있었나)   고치지 않는다 · 취소 후 재등록 (ADR 014)
```

마스터를 지우면 옛 기록이 무엇을 가리키는지 사라진다. 그래서 둘로 막았다 — DELETE 정책이 없고,
가리키는 기록이 있으면 FK 가 23503 으로 거절한다. 이 프로젝트의 **첫 UPDATE 정책**(019)은
마스터에만 있다. 막힌 UPDATE 는 에러 없이 0줄이라 화면은 `.select()` 로 돌려받아 0줄이면 "권한 없음" 을 말한다.

### ③ 비가동 — 같이 설계했다

요구는 OEE 가용성(돈 시간 ÷ 돌기로 한 시간)이다. 증거는 샷의 틈 — S14 에 2시간 20분 ~ 87시간이
비어 있다. **멈춘 흔적은 있고 이유는 없다.** 네 갈림길을 골랐다.

```
구간 한 줄 / 멈춤 · 재개 두 줄         → 구간 — 짝이 안 맞는 줄이 안 생기고, LOT 의 EXCLUDE 를 그대로 쓴다
명단 + 코드 / 글자                      → 명단 — ① 의 갈라짐
명단에 planned / 구분 없음               → planned — OEE 는 계획 정지를 "돌기로 한 시간" 에서 뺀다
사람이 기록 / 샷 틈으로 자동              → 사람 — 자동은 사유가 전부 "미상" 이고 N 분을 정할 근거가 없다
```

겹침은 설비만 본다(제품 칸 없음) — 설비가 멈추면 제품과 상관없이 멈춘 것이다.
`[시작, 끝)` 반열린이라 딱 붙은 두 구간은 겹침이 아니다(ADR 006). 실측 — 08:00~08:30 뒤에 08:30~09:00 저장.

`downtime_not_future CHECK (ended_at <= now())` — Postgres 는 CHECK 를 "안 바뀌는 규칙" 으로 가정한다.
"끝 ≤ 지금" 은 한 번 참이면 계속 참이라 그 가정과 어긋나지 않는다. 반대 방향(`> now()`)이었다면 내일 깨진다.

### ④ 불량 사유는 코드로 바꾸지 않고 명단만 붙였다

`fail_reason` 을 쓰는 곳이 일곱이다(시뮬레이터 · 수집기 · 인덱스 · View · RPC · 화면 둘).
코드로 바꾸면 일곱 곳을 다 고친다. 글자를 그대로 키로 쓰는 명단을 붙이면 **하나도 안 고치고**
갈라짐을 막는 효과는 같다. 이름 바꾸기는 `ON UPDATE CASCADE` 에 맡긴다.

이미 데이터가 있는 칸이라 **만들기 → 채우기(`INSERT … SELECT DISTINCT`) → 묶기** 순서로 걸었다.
묶는 순간 5,314줄을 검사한다. FK 는 NULL 을 보지 않아 양품은 그대로 통과한다.

### ⑤ 수집기에도 반쪽이 있었다

수집기는 `shot` 과 `shot_part` 를 요청 둘로 넣는다 — 트랜잭션 둘. 명단에 없는 사유가 오면 `shot` 만
들어간다(부품 없는 샷). 9월부터 있던 구조인데 명단을 걸면서 실제로 터질 길이 생겼다.
**아는 이유는 쓰기 전에 거절한다** — 모르는 제품 검사 옆에 사유 검사를 두었다.
수집기의 명단은 `active` 로 거르지 않는다. DB 의 FK 보다 엄격하면 둘의 규칙이 어긋난다.

### ⑥ 입력칸의 시각에는 "어디의" 가 없다

`datetime-local` 은 `"2026-10-20T09:00"` 만 보낸다. 서버가 그냥 읽으면 서버의 시간대로 읽는다.

```
서울 PC 에서 그냥 읽기     00:00Z  (맞음)
UTC(Vercel)에서 그냥 읽기  09:00Z  (9시간 늦음)
+09:00 을 붙여 읽기         00:00Z  (어디서든 같다)
```

**개발할 땐 맞고 배포하면 틀린다.** 받자마자 `+09:00` 을 붙인다 — "저장은 UTC, 표시는 KST" (ADR 002) 의 입력 쪽.
배포본에서 08:00 → DB `23:00Z` → 표 08:00 을 확인했다.

## 버린 대안

**① 비가동을 멈춤 · 재개 이벤트 두 줄로**
설비 신호와 닮았다. 버린 이유 — 재개 없는 멈춤 같은 짝이 안 맞는 줄이 생기고, 길이를 낼 때마다 짝을 맞춰야
한다. 겹침을 DB 가 막을 수도 없다.

**② 샷 틈으로 비가동을 자동 생성**
빠지는 게 없다. 버린 이유 — 사유가 전부 "미상" 이라 OEE 의 손실 분석에 쓸모가 없고, "몇 분 이상이면 멈춤" 의
기준이 없다. 기록 안 된 틈을 찾아 알려주는 일은 데이터 구멍 감지에 남긴다.

**③ 진행 중 비가동을 `infinity` 로 받기**
LOT 처럼 열고 닫는다. 버린 이유(이번엔) — 닫을 때 끝 시각을 채우는 UPDATE 가 필요한데 사람이 쓰는 기록은
고치지 않기로 했다(ADR 013). 열고 닫기를 어떻게 "고치지 않고" 할지 정해야 한다.

**④ 불량 사유를 코드(`fail_code 'GAS'`)로 바꾸기**
이름을 자유롭게 바꾸고 다국어에도 대비된다. 버린 이유 — 일곱 곳을 고친다. 둘 다 지금 필요 없다.

**⑤ 수집기가 DB 보다 엄격하게 (active 인 사유만)**
사용 중지된 사유를 설비가 보내는 걸 막을 수 있다. 버린 이유 — 설비가 보내는 건 사실이다. DB 는 받는데 수집기만
거절하면 두 규칙이 어긋나고 원인을 찾기 어렵다.

**⑥ 마스터를 진짜로 지우기 (ON DELETE CASCADE)**
화면이 단순하다. 버린 이유 — 사유 하나를 지우면 그 사유의 비가동 기록이 같이 사라진다. 기록은 감사 대상이다.

## 🔴 따라오는 것

- **이미 데이터가 있는 칸에 제약은 만들기 → 채우기 → 묶기.** 묶는 순간 전부 검사한다
- **실험은 한 번에 규칙 하나만 어긴다.** 둘을 어기면 먼저 검사되는 쪽(CHECK · NOT NULL → UNIQUE · EXCLUDE → FK)이 이름을 댄다
- **실험의 정리 코드는 돌려받은 PK 로 그 한 줄만 지운다.** 넓은 칸(`lot_id` · `product_id`)으로 지우면 진짜 데이터가 같이 지워진다
- **수집기는 이미지로 굽는다** — 코드를 바꾸면 `docker compose up -d --build`
- **수집기의 명단은 시작할 때 한 번 읽는다** — 명단에 사유를 넣으면 수집기를 다시 켠다
- **새 상태가 생기면 옛 화면이 거짓말한다** — 로그인을 붙일 때 메뉴를 안 숨겼다(10/20 사용자 발견)
- **ERD 의 유일한 점선** = `production_lot` ~ `shot` (FK 아님 · ADR 001). 표를 바꾸면 `docs/schema.md` 도

## 남은 것

- **진행 중 비가동** — "고치지 않고" 열고 닫는 방법 (예: 닫기 = 새 줄 · 열린 줄은 View 로)
- **수집기의 근본적 반쪽** — `shot` + `shot_part` 를 RPC 하나로 (S09)
- **기록 안 된 멈춤 찾기** — 샷 틈과 비가동 기록을 비교해 알려주기
- **불량 입력 화면이 생기면** 사용 중지된 불량 사유를 고르는 목록에서 뺀다 (지금은 표시만)
- **OEE** — 실적(사람)과 샷 수(설비)가 어긋날 때 무엇을 믿을지. 계획 정지를 어떻게 뺄지
