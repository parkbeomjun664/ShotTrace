# 008. 집계는 DB에서 한다 — View 와 RPC 로 옮긴다

- **상태**: 채택
- **날짜**: 2026-09-10
- **관련 모듈**: M11
- **관련 파일**: `db/migrations/004_views.sql` · `db/migrations/005_rpc.sql`

## 무엇을 정했나

화면에서 `reduce` 로 하던 집계를 **DB 로 옮긴다.** 조건이 없으면 View, 있으면 RPC.

| View | 내용 | 행 |
|---|---|---|
| `daily_yield` | 계획일별 생산·양품·불량·수율 | 13 |
| `defect_pareto` | 불량 사유별 건수와 전체 대비 비율 | 3 |

두 View 모두 **`WITH (security_invoker = on)`** 을 붙인다.

**조건이 필요한 조회는 View 로 못 만든다.** LOT 상세는 `lot_id` 를 받아야 하므로
`get_lot_shots(p_lot_id text)` 함수(RPC)로 만든다. 시간 구간 조인 규칙
(ADR 001·005·006)이 **DB 안에 한 번만** 정의된다.

함수에는 `LANGUAGE sql` · `STABLE` · `SECURITY INVOKER` · `SET search_path = ''` 를 붙인다.
`search_path` 를 비우면 함수 안에서 `public.` 을 직접 적어야 하지만,
**함수가 가짜 테이블을 읽게 만드는 공격**을 막는다.

`ORDER BY` 는 View 에 넣지 않는다. 정렬은 조회하는 쪽이 정한다.

## 왜

### 전송량이 행 수에 비례하지 않게 된다

지금은 합계 하나를 보여주려고 LOT 전체를 받아 서버에서 더한다.

| LOT 수 | 화면에서 계산 | View |
|---|---|---|
| 25 | 25행 전송 | 1~13행 |
| 1,000 | 1,000행 전송 | 1~13행 |
| 100,000 | 100,000행 전송 | 1~13행 |

집계는 **데이터가 있는 곳**에서 하는 것이 가장 싸다.

### `security_invoker` — 이걸 빼면 View 가 RLS 를 우회한다

Postgres 의 기본값은 **View 를 만든 사람의 권한**으로 실행하는 것이다.
그러면 밑에 깔린 테이블의 RLS 정책이 적용되지 않는다.

지금은 정책이 `read_all` 하나뿐이라 차이가 없지만, S06 에서 역할별 정책
(*"작업자는 자기 설비만"*)을 걸면 **View 로 조회할 때만 전부 보이게 된다.**
에러가 나지 않아서 뚫린 것을 모른다.

Supabase 에서 View 를 만들 때는 항상 붙인다.

### 새로 보인 사실

`daily_yield` 를 만들자마자 화면에 없던 것이 보였다.

```
불량 60건이 6일에 몰려 있다. 13일 중 7일은 무결점.
가장 나쁜 날은 2020-11-04 — 71개 중 7개 불량, 수율 90.14%.
```

현황판의 "전체 수율 98.85%" 만으로는 보이지 않는다.
**5,232행일 때 안 보이던 것이 13행으로 접으니 보인다.**

## 버린 대안

- **화면에서 계속 `reduce`** — 25행이라 지금은 동작한다. 하지만 실시간 파이프라인이
  붙으면 행이 계속 늘고, 그때는 화면 코드를 고쳐야 한다. **구조가 이미 틀렸다.**

- **`production_lot` 에 집계 컬럼을 저장** — 조회는 가장 빠르다. 대신 LOT 이 바뀔 때마다
  갱신해야 하고, 갱신을 놓치면 **조용히 틀린 값**이 남는다. 지금 규모에서는 View 로 충분하다.
  Materialized View 도 같은 이유로 보류한다 — 갱신 시점을 관리해야 한다.

- **PostgREST 집계 함수** (`?select=total_qty.sum()`) — View 없이도 된다.
  하지만 집계 로직이 화면 코드의 문자열 안에 흩어진다. **이름이 붙은 View 가
  재사용과 테스트에 낫다.**

## 생성된 타입은 완벽하지 않다

같은 DB인데 방향이 반대로 틀린다.

| | 생성된 타입 | 실제 |
|---|---|---|
| View | 전부 `\| null` | NULL 이 안 오는 컬럼도 많다 — 과하게 안전 |
| RPC | 전부 non-null | `fail_reason` 은 양품일 때 NULL 이 온다 — **거짓말** |

`RETURNS TABLE` 에는 `NOT NULL` 을 적을 자리가 없어서 생성기가 낙관적으로 본다.
아는 곳은 손으로 좁힌다.

```ts
export type LotShot = Omit<RpcRow, "fail_reason"> & { fail_reason: string | null };
```

**타입을 손으로 고칠 때는 왜 고쳤는지 남긴다.** 안 그러면 다음 사람이 되돌린다.

## 남은 것

- 현황판(`app/page.tsx`)의 `summarize()` · `byEquipment()` 는 아직 화면에서 계산한다.
  `getLots()` 를 대체할 View 를 만들 때 함께 옮긴다.
- `defect_pareto` 는 부분 인덱스 `idx_shot_part_defect` 를 쓴다(ADR 007).
  실제로 쓰이는지 EXPLAIN 으로 확인할 것.
- 소수 자릿수는 View 에서 `ROUND` 해도 JSON 으로 오면서 뒤의 0이 사라진다
  (`25.00` → `25`). 화면에서 `toFixed(2)` 로 한 번 더 맞춘다.
  **DB는 값을 주고 화면은 모양을 정한다.**
