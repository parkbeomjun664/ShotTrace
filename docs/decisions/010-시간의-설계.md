# 010. 시간의 설계 — 이벤트/처리 시각 분리와 진행 중 LOT

- **상태**: 채택
- **날짜**: 2026-10-02
- **관련 모듈**: M17 ★
- **관련 파일**: `008_received_at.sql` · `009_lot_open.sql` · `services/collector/collector.py`
- **관련 ADR**: [001](001-시간구간-조인-구조.md) · [002](002-타임존.md) · [006](006-LOT-경계.md)

## 무엇을 정했나

실시간 파이프라인이 붙으면서 시간에 관한 질문이 셋 생겼다. 셋을 한 번에 정한다.

| 질문 | 결정 |
|---|---|
| 재생 중 `measured_at` 에 무엇을 넣나 | **원본 그대로.** 바꾸지 않는다 |
| 그러면 "방금 들어온 것" 은 어떻게 아나 | **`shot.received_at` 을 새로 만든다** |
| 안 끝난 LOT 의 `ended_at` 은 | **`'infinity'`.** `NULL` 이 아니다 |

그리고 열린 구간이 만드는 사고를 **DB 가 막는다**.

```sql
EXCLUDE USING gist (
    equip_cd                        WITH =,
    product_id                      WITH =,
    tstzrange(started_at, ended_at) WITH &&
);
```

## 왜

### 시각이 두 종류다

```
이벤트 시각 (event time)       그 일이 실제로 일어난 때
처리 시각  (processing time)   시스템이 그걸 안 때
```

진짜 설비면 0.1초 차이라 구분할 필요를 못 느낀다. **차이가 벌어지는 순간 전부
갈린다** — 배속 재생 중이거나, 네트워크가 30분 끊겼다 복구되거나, 설비가
오프라인으로 모았다 한꺼번에 올릴 때.

ADR 002 가 9/1 에 이미 적어뒀다 — *"M17에서 배속 재생을 하면 두 시각이 6년
차이가 난다."* `timestamptz` 를 고른 이유가 그것이었다.

### `measured_at` 을 건드리면 시각만 바뀌지 않는다

배속만큼 압축해서 "지금"으로 옮기는 안을 검토했다가 버렸다.

```
cycle_time 컬럼    59.52초     "이 샷은 59.52초 걸렸다"
measured_at 간격   0.017초     "샷이 0.017초마다 나왔다"
```

**같은 행 안에서 두 숫자가 서로를 부정한다.** `cycle_time` · LOT 의
`started_at`/`ended_at` · 일별 집계가 전부 `measured_at` 을 전제로 서 있다.

### `NULL` 과 `'infinity'` 는 뜻이 다르다

```
NULL        "값이 없다 · 모른다"
'infinity'  "끝이 없다 · 아직 안 왔다"
```

진행 중 LOT 의 끝은 **모르는 게 아니라 아직 안 온 것**이다.

실무적으로도 `'infinity'` 가 싸다. `NULL` 이면 조인마다
`OR ended_at IS NULL` 이 붙고, **한 군데만 빼먹으면 진행 중 LOT 이
조용히 사라진다.** 지금 그 조건이 들어간 곳은 RPC·View·앞으로 쓸 쿼리 전부다.

무한대는 비교가 그냥 되므로 **SQL 을 한 글자도 안 고쳤다.**
`CHECK (ended_at > started_at)` 도 통과한다.

### 그런데 공짜가 아니었다 — 비용이 화면으로 갔다

```
PostgREST   "ended_at": "infinity"      문자열로 나온다
JavaScript  new Date("infinity")        Invalid Date
Intl        RangeError: Invalid time value
```

LOT 상세 화면이 그대로 터졌다. **경계를 넘으면 타입이 바뀐다** — SQL 의 진짜
값이 JSON 에서는 그냥 문자열이다.

`lib/format.ts` 에 `진행중(iso)` 하나를 두어 **`"infinity"` 를 아는 곳을 한
군데로** 모았다 (ADR 002 가 요구한 "포맷은 한 곳에서").

### 열린 구간은 미래를 전부 삼킨다

S14 / CN7 LH 는 LOT 이 6개, 합 1,985개다.

| | |
|---|---|
| `S14-20201016-CN7LH` 원래 | 187개 |
| 그것을 `'infinity'` 로 열면 | **1,985개** (10.6배) |

뒤의 LOT 5개 것을 자기 것이라 주장하고, **뒤의 LOT 들도 여전히 자기 것이라
주장한다.** 한 부품이 두 LOT 에 속한다.

ADR 006 이 반열린 구간 `[시작, 끝)` 을 고른 이유가 "겹치지 않게" 였는데,
**끝이 무한대면 그 보장이 통째로 날아간다.**

진짜 공장이면 열린 LOT 뒤에 닫힌 LOT 이 있을 수 없다. 시간은 앞으로만 간다.
**그래도 "안 터질 것" 에 기대지 않는다** — 작업자가 마감을 깜빡하고 다음
작업지시가 들어오면 똑같이 일어난다. 현장에서 흔한 사고다.

### 겹침은 `UNIQUE` 로도 `CHECK` 로도 못 막는다

```
UNIQUE    같은 값이 두 번 있으면 안 된다     한 컬럼(들)의 값
CHECK     한 행 안에서 조건을 만족해야 한다
EXCLUDE   이 조합이 동시에 존재하면 안 된다   ← 겹침은 두 행 사이의 관계다
```

`UNIQUE` 는 `WITH =` 만 쓰는 **특수한 EXCLUDE** 다. `tstzrange(a,b)` 는
`[a,b)` 반열린 구간 타입이고 `&&` 가 "겹친다" 이므로, ADR 006 에서 손으로
`>=` 와 `<` 를 쓴 규칙이 **타입 하나로 표현된다.**

기존 25개 LOT 을 (설비, 제품) 별로 묶어 겹치는 쌍을 먼저 세어봤다 — **0개.**
제약은 "지금부터" 가 아니라 "지금까지도" 검사하므로, 걸기 전에 확인하는 것이
순서다.

실제로 막는 것을 확인했다.

```
ERROR 23P01: conflicting key value violates exclusion constraint "lot_no_overlap"
DETAIL: (S14, 1, ["2020-10-16 04:58:48+00", infinity)) conflicts with
        (S14, 1, ["2020-10-19 23:24:46+00","2020-10-20 06:20:15+00"))
```

### 수집기는 LOT 을 만들지 않는다

메시지에 `lot_id` 도 `plan_date` 도 없다. **이번엔 메시지가 맞다.**

계획일은 **작업지시(work order)** 에서 온다. 생산관리가 만들고 설비는
받아보지도 않는다. 설비가 아는 것은 압력·온도·시간뿐이다.

LOT 과 샷을 잇는 것은 시간이다 — 그게 ADR 001 이고, *"설비가 LOT 을 몰라도
어느 LOT 인지 알 수 있다"* 가 그 설계의 요점이었다. LOT 생성은 S06(실적 입력)
의 일이다.

## 버린 대안

**① `measured_at` 을 벽시계로 덮기**
진짜 실시간처럼 보인다. 버린 이유 — 2020년 LOT 25개가 전부 빈 껍데기가 되고,
"이 샷이 어느 LOT 것인지" 가 사라진다.

**② 원본 + 고정 오프셋**
오늘 데이터처럼 보인다. 버린 이유 — 3600배속이면 벽시계 1분에 데이터가
60시간 가므로 **미래 시각이 찍힌다.**

**③ 배속만큼 압축**
벽시계와 맞는다. 버린 이유 — `cycle_time` 과 `measured_at` 간격이 서로를
부정한다. **데이터가 자기모순에 빠진다.**

**④ `ended_at` 을 `NULL` 로**
"모른다" 의 표준 표현이다. 버린 이유 — 조인마다 `OR IS NULL` 이 붙고 한 군데만
빼먹으면 조용히 사라진다. 그리고 뜻이 다르다.

**⑤ `ADD COLUMN received_at timestamptz DEFAULT now()` 한 줄로**
간단하다. 버린 이유 — **기존 2,626행 전부에 "지금" 이 채워진다.** 9월 초에
CSV 로 넣은 행이 "2026-09-30에 수집기로 받았다" 고 말하게 된다. 두 줄로 나눠
기존 행을 `NULL` 로 남기면, 그 `NULL` 이 **"CSV 로 직접 들어왔다"** 는 정보가 된다.

**⑥ 수집기가 LOT 을 자동 생성**
LOT 없는 샷이 안 생긴다. 버린 이유 — 설비는 계획일을 모른다. `measured_at` 의
날짜로 치면 야간 교대가 자정을 넘길 때 LOT 이 쪼개진다. 그리고 ADR 001 의
전제(설비는 LOT 을 모른다)를 깬다.

## 결과로 따라오는 것

- **`received_at - measured_at` 이 파이프라인 지연**이다. 진짜 설비면 0.2초쯤이고
  30초로 늘면 어딘가 막힌 것이다. 재생 중에는 6년이라 의미가 없다.
- **시계·난수·UUID 는 함수 안에서 만들지 않는다.** `to_shot_row(msg, now)` 처럼
  밖에서 받는다. 안에서 `datetime.now()` 를 부르면 같은 입력에 다른 출력이 나와
  테스트를 쓸 수 없다.
- **`'infinity'` 를 화면에 그대로 보내지 않는다.** `진행중()` 을 거친다.
- **LOT 을 닫는 것은 언제나 안전하다.** 구간이 줄어들 뿐이라 EXCLUDE 에 걸리지 않는다.
- **새 상태를 만들면 그 상태를 모르는 코드가 깨진다.** SQL 은 멀쩡했고 화면이 터졌다.

## 남은 것

- **미할당 생산** — LOT 없이 들어온 샷은 화면에 안 보이고 수율에도 안 잡힌다.
  작업자가 LOT 을 안 열고 기계를 돌리면 실제로 일어난다. 보이게 할 방법을 정해야 한다.
- **`production_lot` 의 저장 집계** — `total_qty`/`pass_qty`/`fail_qty` 가 저장값이라
  진행 중 LOT 에서는 즉시 낡는다. ADR 008 이 이미 경고한 것(*"갱신을 놓치면
  조용히 틀린 값이 남는다"*)이 실시간에서 현실이 된다.
- **`DROP NOT NULL` 미검증** — `shot_part.part_id` 가 nullable 이 됐지만, 기존
  2,626샷이 전부 UPDATE 라 INSERT 경로를 아직 한 번도 안 탔다.
