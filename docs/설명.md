## 10초 · 한 문장

사출성형 공장의 MES인데요, **LOT과 설비 상태를 시간 구간으로 이어서**, 불량이 난 LOT을 만들 때 설비가 어땠는지를
바로 볼 수 있게 만들었습니다.

## 30초

사출성형 공장의 MES입니다. 현장에서 LOT을 추적하는 진짜 목적은 "그 LOT을 만들 때 설비가 어땠나" 라고 들어서,
설비 데이터에 LOT 번호를 붙이지 않고 설비와 시간 구간으로 잇는 구조로 만들었습니다.

실제 공개 데이터 5천 건을 MQTT로 실시간 재생해 화면까지 흐르게 했고, 실적 장부는 고칠 수 없게 하고 취소와 정정만
되도록 DB에서 막았습니다.

데이터를 10배로 늘려도 LOT 조회는 1밀리초 아래로 버티는 것을 측정했고, 테스트 25개가 푸시할 때마다 CI에서 돕니다.

## 1분 · 그림 한 장 (손으로 그리며)

```
CSV ─▶ 시뮬레이터 ─▶ MQTT ─▶ 수집기 ─▶ PostgreSQL ─▶ Next.js 화면
                                         │  ▲
                                         └──┘ 변경 알림 (Realtime)
```

- 공개 데이터를 시뮬레이터가 실제 시간 순서대로 MQTT 로 보낸다 — 실제 공장이라면 PLC · 게이트웨이 자리
- 수집기가 받아 Postgres 에 넣는다 — 같은 메시지가 두 번 와도 PK 가 막아 한 줄 (QoS 1 · 멱등)
- 화면은 DB 가 "바뀌었다" 고 알려주면 그때 다시 읽는다 — 알림의 값을 쓰지 않으니 몇 개 놓쳐도 틀리지 않는다 (ADR 012)
- 권한은 화면이 아니라 DB 의 RLS 가 막는다 — 공개 읽기 전용 계정으로 직접 확인 가능 (ADR 013)

## 5분 · 결정 셋

### ① 왜 시간 구간 조인인가 — [ADR 001](decisions/001-시간구간-조인-구조.md)

설비는 지금 어떤 LOT 을 만드는지 모른다. 그래서 신호에 LOT 을 붙이지 않고, 볼 때 설비 + 시간으로 찾는다.
현장 MES 는 "지금 이 설비가 하는 작업" 에 신호를 **쓸 때 붙인다**. 나는 늦게 온 신호 · LOT 경계 수정에 강한
**읽을 때 잇기**를 골랐고, 조인 비용은 인덱스로 감당했다. 10배 데이터에서 인덱스 유무 차이가 4.5배 → 30배로
벌어지는 걸 측정했다 ([evidence/perf-10x](evidence/perf-10x.md)).

### ② 왜 장부는 고칠 수 없나 — [ADR 013](decisions/013-인증과-인가.md) · [014](decisions/014-취소와-정정.md)

제조 기록은 감사 대상이라 UPDATE 정책을 아예 만들지 않았다. 정정은 취소 장부에 빨간 줄을 긋고 새 줄을 쓰는 것을
함수 하나(트랜잭션 하나)로 묶었다. 두 사람이 동시에 정정하는 건 트랜잭션으로 못 막아서, 취소 장부의 PK 를 원래 줄
번호로 두어 DB 가 두 번째를 거절하게 했다 — 두 요청을 동시에 보내 한 명만 성공하는 걸 확인했다.

### ③ 조용히 틀리는 것을 어떻게 막았나

에러 없이 숫자만 틀리는 경우가 가장 무서웠다. 제약을 종류별로 일부러 어겨보는 실험으로 13개 모두 DB 가 막는 것을
확인했고 ([evidence/constraints-reject](evidence/constraints-reject.md)), OEE 성능은 100% 에서 자르기 **전** 값도
꺼내두어 LOT 경계가 한 사이클 짧던 버그를 찾았다 ([ADR 016](decisions/016-OEE.md)). 규칙들은 테스트 25개로 묶어
CI 가 매번 돌린다.
