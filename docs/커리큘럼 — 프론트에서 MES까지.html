6개월치 커밋 이력은 나중에 만들 수 없다. 그리고 .gitignore 없이 첫 커밋을 하면 나중에 키를 지워도 이력에 영원히 남는다. 순서가 중요한 유일한 모듈.

배울 것

  • 커밋 메시지 — "무엇을"이 아니라 "왜". 6개월 뒤의 내가 독자
  • 1인 프로젝트의 브랜치 전략 — 복잡한 건 필요 없지만 기능 단위 브랜치는 이력을 읽기 좋게 만든다
  • .gitignore · .env · .env.example — 키가 저장소에 올라가면 무슨 일이 벌어지나
  • Node 버전 고정 · Python 가상환경(venv) · Docker Desktop 설치 확인

M02백엔드 사고방식 전환8/17 · 반나절

프론트에서 백엔드로 넘어올 때 진짜 벽은 문법이 아니라 "이 값을 누가 믿을 수 있는가"다. 이걸 안 잡고 Supabase를 쓰면 anon key로 테이블이 통째로 열린 채 배포된다.

배울 것

  • 신뢰 경계(trust boundary) — 브라우저에서 온 값은 전부 거짓말일 수 있다
  • 코드가 실행되는 세 곳 — 서버 / 클라이언트 / DB. 각각 무엇을 믿을 수 있나
  • Supabase를 쓴다는 건 DB를 브라우저에 반쯤 노출한다는 뜻이라는 사실
  • ISA-95 Level 3에서 MES가 지는 책임 = 기록의 진실성
산출물화면 6개 각각의 "누가 읽고 누가 쓰나" 표 → 11월 M17 RLS 정책의 초안

일정이 밀렸을 때 — 버리는 순서

6개월 계획은 반드시 어딘가 밀린다. 그때 즉흥적으로 정하면 가장 중요한 걸 버리게 된다. 미리 정해둔다.

순위구간판단
절대 사수M01~M20 (10월 MVP + 11월 기록) + M28 (설명)여기까지가 완결된 제품이다. 설명 못 하면 만든 것도 소용없으니 M28도 사수
버림 ①M23 LLM 연동 (3일)가장 화려하지만 없어도 MES는 완결이다. 시간이 없으면 매핑표 기반 정적 규칙만 남기고 AI는 뺀다
버림 ②M21 데이터 모델링 (1일)downtime 테이블을 안 만들면 OEE 가용성을 못 구한다 → M22와 함께 축소
버림 ③M26 관측성 절반 (1일)CI는 남기고 에러 추적·헬스체크를 뺀다. CI 배지가 가성비가 가장 좋다

학습이 원인이면 → 그 모듈을 압축하지 말고 질문 빈도를 올린다(30분 규칙을 15분으로).
개발이 원인이면 → 기능 범위를 줄인다. 화면 하나를 덜 예쁘게 만드는 건 손해가 아니다.
08

선결 리스크 — 지금 안 정하면 비싸지는 것

  • BETWEEN은 양끝을 포함한다M07 LOT A의 ended_at과 LOT B의 started_at이 같으면 그 샷이 양쪽에 모두 잡힌다. 수율이 미세하게 틀어지고 원인 추적이 매우 어렵다. 반열린 구간을 표준으로 채택할지 지금 정한다.
  • 타임존M03 KAMP TimeStamp는 타임존 정보가 없다. timestamp냐 timestamptz(KST)냐를 적재 전에 확정해야 한다. 10월에 9시간 어긋난 걸 발견하면 전체 재적재다.
  • 한글 날짜 형식M06 PART_FACT_PLAN_DATE가 "2020-10-16 오전 12:00:00"이다. 표준 파서로는 안 읽힌다. "오전 12시"가 자정인지 정오인지도 데이터로 확인해야 한다.
  • ended_at이 NULL인 진행중 LOTM15 · M20 정적 데이터엔 없지만 실시간엔 항상 있다. 쿼리·인덱스·화면이 전부 이 경우를 감당해야 한다. 10월에 급조하면 화면 로직이 흔들린다.
  • Vercel에 수집기를 올릴 수 없다M15 서버리스에는 상시 프로세스가 없다. MQTT 구독을 유지할 곳이 따로 필요하다. 10월 4주에 부딪히지 말고 미리 알고 간다.
  • 죽은 컬럼 12개를 스키마에 남길 것인가M03 · M21 빼면 깔끔하지만 실제 설비 교체 시 살아날 수 있는 값이다. 어느 쪽이든 판단 근거를 ADR로 — "왜 45개가 아니라 33개입니까"는 반드시 나온다.
  • 키를 커밋하면 지워도 이력에 남는다M01 공개 저장소라 더 위험하다. .gitignore를 첫 커밋 전에 만들어야 하는 이유. 순서가 중요한 유일한 항목.
  • 무료티어엔 자동 백업이 없다M04 · M26 8~10월 데이터는 ETL 재실행으로 복원되지만, 11월 이후 사람이 입력한 실적은 날아가면 끝이다. 미사용 시 프로젝트 일시정지도 있다. M26에서 백업 절차와 데모 전 점검을 문서화한다.
  • RPC 안의 동적 SQLM10 Supabase 클라이언트를 쓰면 인젝션이 대부분 막히지만, Postgres 함수 안에서 문자열을 이어붙여 EXECUTE하면 그대로 뚫린다. 파라미터 바인딩을 원칙으로.

면접 문장 지도 — 각 모듈이 남기는 것

모듈은 배움으로 끝나지 않고 말할 수 있는 한 문장을 남긴다. 이게 커리큘럼의 최종 산출물이다.

모듈남는 문장
M016개월간 하루 단위로 커밋했고, 설계 결정은 그때그때 ADR로 남겼습니다
M04스키마는 전부 마이그레이션 파일로 관리해서, DB를 지워도 5분이면 복원됩니다
M06적재 스크립트를 멱등하게 만들어서 몇 번을 돌려도 데이터가 중복되지 않습니다
M07 ★인덱스를 (equipment_id, measured_at) 순서로 잡은 건 왼쪽 접두사 규칙 때문이고, 반대로 걸었을 때 EXPLAIN을 비교해 확인했습니다
M09화면마다 "이 화면이 답하는 질문"을 먼저 정하고 거기서 쿼리를 역산했습니다
M10집계는 전부 DB에서 끝냅니다. 클라이언트에서 수천 행을 도는 코드가 없습니다
M14MQTT는 at-least-once라 중복이 옵니다. 원본 샷 ID를 PK로 써서 upsert로 멱등하게 처리했습니다
M15 ★과거 데이터를 배속 재생하다 보니 "지금"을 무엇으로 볼지가 문제였고, ○○로 정한 이유는 이렇습니다
M17권한은 RLS로 DB에서 막습니다. 화면에서 버튼을 숨기는 건 편의고 실제 방어선은 그 아래입니다
M18검증은 폼·서버·DB 세 군데서 합니다. 앞의 둘은 UX와 보안이고, 마지막은 최후의 방어선입니다
M19 ★실적은 수정이 안 되고 취소 후 재등록만 됩니다. 제조 기록은 감사 대상이라 덮어쓰면 안 되기 때문입니다
M20LOT 시간 구간이 겹치는 건 EXCLUDE 제약으로 DB가 막습니다. 코드가 실수해도 데이터는 안 깨집니다
M21운영 중인 DB에 테이블을 추가할 때 되돌릴 수 있게 마이그레이션을 썼습니다
M22OEE는 세 요소를 각각 저장합니다. 합친 값 하나만 남기면 어디가 문제인지 알 수 없어서입니다
M23LLM에 매핑표와 실제 그 시점의 공정 데이터를 함께 넣습니다. 근거 없이 답하지 않게 하려고요
M25수십만 건까지 늘려서 인덱스가 실제로 버티는지 측정했고, 수치는 문서에 남겼습니다
M26수집기가 죽으면 화면에 데이터 구멍 경고가 뜹니다. 조용히 실패하는 게 가장 위험해서요
가장 강한 한 문장은 그대로 "현장에서 추적하는 목적이 자재가 아니라, 그 LOT을 만들 때 설비가 어땠나를 보는 거라고 들어서, 시간 구간 조인 구조로 만들었습니다."

M07 · M15 · M20을 마치면 이 문장 뒤에 붙는 모든 꼬리질문에 답할 수 있다. 커리큘럼의 목적지가 여기다.
